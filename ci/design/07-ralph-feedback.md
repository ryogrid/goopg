# 07 — Feeding Failures Back into the Ralph Loop

Requirement: a test that FAILs in the nightly batch must become the
**top-priority task** inside the Ralph loop. Two pieces make that happen:

1. the batch generates an **agent-readable action-items log** at a stable
   path, so the in-loop agent can see "what needs fixing" in one Read;
2. `.ralph/fix_plan.md` carries a **standing, top-priority triage milestone**
   that instructs the agent to convert those items into tasks and execute
   them before anything else.

The batch writes the log; the *agent* (not the batch) writes the fix_plan
tasks. The batch never edits `.ralph/` files: `.ralph/fix_plan.md` is
loop-owned state that has been observed to undergo full mid-loop rewrites
(the driver itself only *reads* it — `ralph_loop.sh` greps checkbox counts —
so the rewriter is almost certainly the in-loop agent/subagents; either way
the file changes underneath any concurrent writer). One-way data flow
(batch → log → agent → fix_plan) keeps the batch out of that race entirely.

## A. The action-items log — `ci/logs/action-items.md`

Written by S3 (summarize) on **every** run, derived from `summary.json`.
Stable path (NOT inside the timestamped run dir) so the milestone below can
reference one fixed filename; the run dir keeps nothing extra — the file
cites run-dir evidence paths.

Overwritten wholesale each run: items that passed tonight disappear; new
failures appear. **Absence of a fresh failure is the only removal
mechanism** — the agent never edits this file.

### Format (agent-optimized)

```markdown
# NIGHTLY ACTION ITEMS — generated by ci/batch, DO NOT EDIT
run: 20260707-000012   sha: 04f2f6cf   status: fail
generated: 2026-07-07T02:55:03+09:00
items: 2

## AI-20260707-000012-001  [regression] testport / TestPort_Pgbench001WithServer
- subject: testport/TestPort_Pgbench001WithServer
- what: must-pass oracle port FAILed (port-status row P-006, pass_required=yes)
- repro: go test -v -run 'TestPort_Pgbench001WithServer$' ./internal/testport/
- evidence: ci/logs/20260707-000012/testport/go-test.log
- first-seen: 20260707 (not present in previous run 20260706-000009)

## AI-20260707-000012-002  [regression] tpch / Q21 row count
- subject: tpch/Q21-rows
- what: Q21 returned 312 rows, anchor is 397 (m0093 anchors)
- repro: tmp/tpch-runner -port 65433 -db postgres -user <superuser> -queries 21 -per-query-timeout 1200s   # start server per ci/design/05-tpch-stage.md §A first
- evidence: ci/logs/20260707-000012/tpch/timings.csv, tpch/explain/q21.txt
- first-seen: 20260707

# NON-BLOCKING NOTICES (no action required; harvest opportunistically)
- promotable: isolation deadlock-parallel.spec PASSED (expected-fail) — consider promotion per ci/design/02-test-selection.md §D
- env-drift: pg_amcheck newly skipped (binary missing)
```

Rules:

- **Item id** `AI-<full-run-id>-<seq>` (run id = `YYYYMMDD-HHMMSS`) — unique
  across ALL runs including same-day on-demand `make nightly-batch` runs
  (a date-only id would collide there). The agent cites the id in fix_plan
  tasks and commit messages.
- **`subject:` is the dedup key**, not the id: a stable slug for the
  underlying failure (`<stage>/<test-or-query>`), identical across runs while
  the same thing keeps failing. The id names *this run's observation*; the
  subject names *the problem*. (§B's tracking rule uses the subject —
  otherwise a multi-night failure would spawn one duplicate task per night.)
- **One item per root observation**, kinds drawn from the doc 02 §B
  classification: must-pass FAIL, regress mismatch-skip (baseline-`pass`
  case), TPC-H row-anchor/spotcheck/query-error, `perf-drastic` events,
  `fail(build)`. A run-level `inconclusive` (resource-kill) emits ONE item
  of kind `[investigate]` only when it occurs on **2 consecutive runs**
  (a single co-load kill is noise; doc 03 §C).
- **`repro` must be a copy-pasteable command** (plus a pointer to any server
  setup it needs). This is the single highest-value field for the agent.
- **Non-blocking notices** (promotable, env-drift, plan-drift) go in the
  bottom section and are explicitly not action items — they must not preempt
  feature work.
- Zero-items case: the file still exists, with `items: 0` and no `## AI-`
  sections — the agent's check ("does it contain `## AI-`?") stays a single
  cheap Read.

### Staleness contract

The file reflects **the last nightly run**, which may be many working hours
ago. A fix landed during the day leaves the item stale until the next run.
Therefore the consuming rule (encoded in the milestone below) is: **re-run
the item's `repro` before starting work** — if it passes at HEAD, mark the
task done with a note "already fixed / stale item" instead of investigating.

### Generation notes (S3 implementation details)

- **`first-seen`** is computed by diffing against the **previous run dir's
  `summary.json`** (run dirs are retained 14 deep — doc 04 §E;
  `history.jsonl` carries run-level status only, no per-item data).
- **"2 consecutive `inconclusive` runs"** (the `[investigate]` trigger) is
  read from `history.jsonl` — it does carry per-run status.
- `ci/logs/` is **gitignored**, so AI-ids cited in fix_plan/commits point at
  local-only, eventually-pruned evidence. Acceptable by design (the commit
  message carries the subject and the fix); anyone needing the original
  evidence has 14 days of run dirs.

## B. The standing milestone in `.ralph/fix_plan.md`

Implementation adds this block **at the top of the milestone list** in
`.ralph/fix_plan.md` (and keeps it there permanently — it is a standing
milestone, never completed, never deleted; the driver's completion detector
counts checkboxes, so the instructional comment carries no checkbox):

```markdown
## M-NIGHTLY — Nightly regression triage (STANDING — HIGHEST PRIORITY)
<!-- Standing milestone. Source of work: ci/logs/action-items.md
     (regenerated by every nightly batch run; see ci/design/07-ralph-feedback.md).
     Loop rule:
       1. Read ci/logs/action-items.md (absent file = nothing to do). For
          each `## AI-` item whose `subject:` has no OPEN (unchecked) task
          below: add one task
            - [ ] <subject> — <one-line what> (AI-<id>; repro: <cmd>)
          If an unchecked task for the same subject already exists, do NOT
          add another — append the new AI-id to that task's line instead
          (multi-night persistence of one problem stays ONE task).
          If only a CHECKED task exists for the subject, the failure has
          reopened: add a new task and note the earlier fix didn't hold.
       2. Tasks in this milestone PREEMPT all other milestones (finish an
          already in-flight working_set task first, then come here before
          selecting any new work).
       3. Before investigating, re-run the item's repro at HEAD — the log
          reflects the last nightly run and may be stale; if it passes,
          check the task off with a "stale — already fixed" note.
       4. Fix with the normal gates (practice cards apply), cite the AI-id
          in the commit message, check the task off. The next nightly run
          confirms and drops the item from the log. -->
- [ ] (tasks are added here by the in-loop agent, one per subject)
```

Notes on the mechanics:

- **The agent adds the tasks, inside the loop, as ordinary fix_plan
  editing** — the write path PROMPT.md already mandates ("update
  fix_plan.md with your learnings"). The batch never touches the file (see
  intro). But the same mid-loop churn that keeps the batch out also bites
  the agent's own edits (stale Read → "modified since read" failures — an
  observed failure mode). So the milestone-task write must be
  **churn-tolerant**: re-Read fix_plan.md immediately before the Edit, make
  the smallest possible change (append task lines under M-NIGHTLY only),
  and on an edit-conflict re-read and retry once; if it still conflicts,
  record the pending AI-items in `.ralph/working_set.md` and add them next
  iteration rather than fighting the file.
- The placeholder checkbox is a design decision with a global side effect:
  the driver's `should_exit_gracefully()` counts `- [ ]`/`- [x]` lines
  across the WHOLE file, so one permanently-unchecked box disables the
  `plan_complete` graceful exit for the entire plan. For this project's
  continuous loop that is acceptable (arguably desirable), but it must be a
  conscious choice — if the exit path should stay live, keep the
  placeholder as a comment line instead and rely on the §C PROMPT.md rule
  alone; decide at implementation.
- **Priority is enforced by the file's own convention**: fix_plan.md's
  header rule is "pick the topmost unchecked item **unless the Current
  Priority banner forces another order**" — so implementation does BOTH:
  place M-NIGHTLY at the top of the milestone list AND add one line to the
  `## Current Priority` banner: *"Standing exception: M-NIGHTLY triage items
  (from ci/logs/action-items.md) preempt everything below."* Plus the
  PROMPT.md line (§C). No driver change is needed. (`.ralph/AGENT.md`
  carries a variant of the pick-topmost rule *without* the banner clause —
  topmost placement satisfies that copy too, so both formulations agree.)

## C. One-line hook in `.ralph/PROMPT.md` (implementation edit)

So the agent checks the log even when fix_plan has no M-NIGHTLY tasks yet,
implementation adds to the standing instructions in `.ralph/PROMPT.md`
(exact placement chosen at implementation; the working-set section is a
natural neighbor):

```markdown
- NIGHTLY TRIAGE: after the working_set resume (working_set.md stays the
  very first read), read ci/logs/action-items.md (absent file = skip). If
  it lists `## AI-` items whose subject has no open M-NIGHTLY task in
  fix_plan.md, add them there and work them BEFORE selecting any other
  milestone's work. Finish an already in-flight task first — preemption
  applies at task-selection time, not mid-task. (Rules in the M-NIGHTLY
  comment / ci/design/07-ralph-feedback.md.)
```

Deliberate ordering: `.ralph/working_set.md` keeps its existing "read
FIRST" position (the loop's resume mechanism, injected by
`build_loop_context()`); the triage check is the first step of *task
selection*, so the two "firsts" don't compete. One Read per loop iteration;
with `items: 0` the cost is negligible.

## D. Lifecycle walkthrough

```
night N   : batch fails TestPort_X → action-items.md gains AI-…-001
day N     : loop iteration reads the file → adds task under M-NIGHTLY
            → preempts feature work → re-runs repro (still fails)
            → fixes, gates, commits citing AI-…-001 → checks task off
night N+1 : batch passes TestPort_X → action-items.md regenerated without
            the item (items: 0) → nothing to do
```

Failure-mode handling:

| Situation | Behavior |
|-----------|----------|
| Agent fixed it before reading the log | repro passes at HEAD → task closed as stale (staleness contract §A) |
| Item persists ≥ 2 nights while its task is still OPEN (multi-day fix in progress) | same `subject:` → subject-dedup matches the open task → **no duplicate**; the agent appends the new AI-id to the existing task line |
| Item reappears after its task was CHECKED OFF | same subject but only a checked task exists → **reopened**: new task added, noting the earlier fix didn't hold (flaky or partial fix) |
| Batch itself broke (`fail(build)` from loop's own WIP commit) | `AI-… [regression] build` item — the highest-value item of all; same flow |
| Two loops / an interactive session both read the file | both see the same subjects; dedup-by-subject keeps the task single (and the concurrent-commit pathspec rules apply as usual) |

## E. Explicit non-goals

- The batch does **not** file tasks, edit `.ralph/`, ping the loop, or block
  on the loop's state — one-way file handoff only.
- No auto-revert / auto-bisect: identifying the offending commit is the
  agent's job (the log gives `first-seen` + the run's `sha` to bound the
  bisect range: the regression landed between run N-1's sha and run N's).
- Notices (promotable/env-drift/plan-drift) never preempt — only gating
  failures become AI-items.
