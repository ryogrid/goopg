# M0098-0001: goopg pgbench Baseline Measurement

**Date**: 2026-05-12  
**Commit**: ralph-period-from-0511 (post-M0097 / post-M0093 WAL skip)  
**Conditions**: `-c 100 -j 100 -T 180 -s 100`, `shared_buffers=2560MB`, `wal_buffers=100MB`

| Workload | goopg TPS | Target TPS | Gap | Previous (-c 10) |
|---|---:|---:|---:|---:|
| Standard (TPC-B) | **229** | 1,500 | 6.5× | ~58–70 |

| Select Only | **6,166** | 10,000 | 1.6× | ~2,740 |

## Key Observations

### Standard / Simple Update (229 / 228 TPS)
- M0093 WAL read-only skip helps write workloads too: -c 100 delivers more TPS than -c 10
  (229 vs 58–70 for standard). At higher concurrency the WAL group commit opportunity is larger.
- Failure rate: 9/41,338 = 0.022% for standard (concurrent UPDATE conflicts causing SQLSTATE 40001).
  Root cause: no EvalPlanQual → aborts instead of row-recheck (M0098-0004 target).
- Latency: 424 ms average at -c 100 — consistent with WAL fsync serialization bottleneck
  (each transaction blocks on one fdatasync; at 229 TPS, ~2 WAL flushes/s is very low).
- **Primary bottleneck**: WAL group commit (M0098-0002) — expected 8–15× improvement.

### Select Only (6,166 TPS)
- M0093 read-only WAL skip is working at -c 100: 6,166 TPS vs 2,740 TPS at -c 10 (+2.25×).
- Still short of 10,000 TPS target (1.6× gap).
- Heap profile shows `storage.newArena` = 76.5% of live heap (128 MB / 167 MB).
  This is the buffer pool arena allocator; it's a startup cost, not per-query.
- **Primary bottleneck for select-only**: buffer pool global `poolMu` contention
  at high concurrency (M0098-0003 target — 128-partition LWLock replacement).

## Pprof Summary (inuse_space, post-3-workload-run)

Top allocators:
1. `storage.newArena` — 128 MB (76.5%) — buffer pool arena slabs (one-time startup)
2. `wal.NewMemRing` — 16 MB (9.6%) — WAL ring buffer (one-time startup)
3. `wal.newWALBuffer` — 16 MB (9.6%) — WAL write buffer (one-time startup)

Observation: most live heap is from startup allocations, not per-query. This means
the GC pressure during workload is from transient allocations (rows, parsed queries,
plan nodes) that are collected quickly. The per-query allocation hot-paths from
M0092 profiling likely still apply under high concurrency.
