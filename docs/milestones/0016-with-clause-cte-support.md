# Milestone 0016 — WITH Clause (CTE) Support

**Status:** planned
**Depends on:** Milestone 0001 (core parser/planner/executor pipeline), Milestone 0003 (TPC-H SQL coverage baseline), Milestone 0006 (planner statistics and join-planning maturity).
**Drives:** PostgreSQL-compatible Common Table Expression (CTE) support for practical analytical and application queries, including a staged path from non-recursive WITH to WITH RECURSIVE.

## Context

goopg currently plans and executes SELECT/INSERT/UPDATE/DELETE workloads across a growing subset, but does not support `WITH` clause query factoring. This leaves an important compatibility gap for PostgreSQL-oriented clients and SQL generated by ORMs/BI tooling.

This milestone introduces `WITH` support with a correctness-first staged approach:

- Stage A: non-recursive `WITH` (initial release).
- Stage B: `WITH RECURSIVE` (follow-up in the same milestone).

The objective is to shorten time-to-availability for high-value query factoring patterns while keeping recursive execution semantics explicit and testable.

## In Scope

### SQL Parser and AST

- Parse and represent:
  - `WITH cte_name [(col, ...)] AS (subquery) ...`
  - multiple CTEs in one WITH list
  - `WITH RECURSIVE`
  - CTE references in `SELECT`, `INSERT ... SELECT`, `UPDATE ... FROM`, and `DELETE ... USING` where otherwise supported.
- Preserve clear parser errors and byte-position diagnostics for malformed CTE syntax.

### Analyzer and Name Resolution

- Implement CTE scope rules consistent with PostgreSQL behavior:
  - left-to-right visibility in the WITH list
  - outer query visibility of declared CTE names
  - deterministic handling of name shadowing against base relations/views.
- Validate CTE output column arity and alias rules.

### Planner Integration

- Stage A:
  - support non-recursive CTE planning with a deterministic materialization strategy.
  - treat CTEs as reusable plan producers for downstream consumers in the same statement.
- Stage B:
  - support recursive CTE planning with separate anchor and recursive members.
  - enforce legal recursive shape checks and reject unsupported recursive constructs with stable SQLSTATE errors.

### Executor Integration

- Stage A:
  - execute non-recursive CTEs once per statement and feed one or more consumers.
  - preserve statement snapshot/MVCC consistency across producer/consumer execution.
- Stage B:
  - execute recursive CTEs using iterative fixpoint semantics.
  - provide cycle-safe termination behavior for supported recursive forms.

### Performance and Memory Safety

- Bound CTE materialization memory behavior with explicit safeguards.
- Add fallback behavior for large intermediate CTE results (clear error or bounded spill behavior according to design decisions).
- Ensure CTE execution does not regress existing non-CTE query correctness.

### Testing and Observability

- Add parser/analyzer/planner/executor regression tests for both non-recursive and recursive CTE paths.
- Add compatibility tests against representative PostgreSQL query shapes that rely on WITH.
- Add observability hooks (plan output labels and runtime counters) so operators can identify CTE-heavy workloads.

## Out of Scope

- Full PostgreSQL CTE optimization parity (advanced inlining heuristics, exhaustive cost-based materialization toggles).
- `SEARCH` / `CYCLE` clauses for recursive CTEs.
- Data-modifying CTE chains beyond the subset explicitly supported in this milestone.
- Full spill-to-disk framework redesign (only minimal bounded behavior needed by this milestone).
- Planner-hint-level controls over CTE strategy.

## Definition of Done

### Stage A Gate (Initial Release)

1. Non-recursive `WITH` syntax parses and analyzes correctly, including multi-CTE lists and optional column alias lists.
2. CTE scope and name-resolution behavior matches documented PostgreSQL-compatible rules for supported statement forms.
3. Non-recursive CTE producer/consumer planning and execution work end-to-end with deterministic statement semantics.
4. Multiple consumers of one CTE within the same statement return stable, correct results.
5. Explain/plan output includes clear CTE-related nodes or labels for operator visibility.
6. Regression suite covers parser/analyzer/planner/executor paths for non-recursive WITH.
7. Required design docs `0016-0001` and `0016-0002` are merged with status `accepted`.

### Stage B Gate (Milestone Accepted)

8. `WITH RECURSIVE` parses, analyzes, and executes for supported recursive query shapes.
9. Recursive execution follows anchor-then-iterative semantics and terminates correctly for supported workloads.
10. Unsupported recursive constructs fail deterministically with stable SQLSTATE diagnostics.
11. Recursive CTE execution does not regress correctness of Stage A non-recursive behavior.
12. Compatibility tests demonstrate representative PostgreSQL recursive query shapes working under the supported subset.
13. Required design docs `0016-0003` and `0016-0004` are merged with status `accepted`.
14. End-to-end regression and workload tests remain green with CTE support enabled.
