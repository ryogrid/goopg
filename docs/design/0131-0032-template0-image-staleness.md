# 0131-0032 — Runtime `CREATE DATABASE` inherited a stale template0 image

**Milestone task:** M0131-S15 (S15.1–S15.4)
**Status:** LANDED 2026-08-12
**Measured by:** `0131-0004` finding F4 (`TestE2E_PGColdStartOnGoopgDataDir`)

## The gap

A real PG 18.3 hosted on a goopg data directory serves the `postgres` database
correctly — that is the whole positive result of `0131-0004`. But connecting it
to a database **goopg minted at runtime** with `CREATE DATABASE` took the whole
cluster down:

```
psql: connection to server … failed:
      PANIC:  could not open critical system index 2662
```

2662 is `pg_class_oid_index`. `RelationCacheInitializePhase3`
(`postgres/src/backend/utils/cache/relcache.c`) nails and opens a small set of
critical indexes during `InitPostgres`, and `load_critical_index` failing there
is a **PANIC**, not an ERROR, so the postmaster dies with the connection
attempt.

## Root cause — template0, not the runtime path

The task was filed on the hypothesis that the runtime `CREATE DATABASE` path
"clones only what goopg itself needs". That hypothesis is **wrong**, and this
is the discovery of the slice: `CREATE DATABASE` already copies template0's
entire on-disk image (`initdb.copyBootstrapCatalogImage`, driven by
`CreatePerDatabaseScaffolding` from `server.createDatabasePhysicalDirectory`).
The image it copies was the stale thing.

`bootstrapPostgresDatabase` (`internal/initdb/initdb.go`) materialises `base/4`
**early** in `Init`: it copies the then-current `base/1`, writes
`pg_filenode.map`, and then stamps a 1-page metapage-only btree placeholder over
every per-database index OID. All the populated content — the bulk-loaded
btrees and the wide catalog heaps — is written **later**, by the ~40
bootstrappers that each target `base/1` and `base/5` explicitly
(`internal/initdb/btree_index_bootstrap.go` and friends). Nothing re-visited
`base/4`.

Measured on a fresh `goopg init` before the fix:

| dir | files | `2662` size |
|---|---|---|
| `base/1` (template1) | 122 | 16384 |
| `base/4` (template0) | 89 | **8192** (metapage only, no leaf entries) |
| `base/5` (postgres) | 149 | 16384 |

`base/4` was missing 59 files outright (including the `pg_proc` heap 1255) and
carried empty stubs for 35 more. Every runtime-created database inherited that.
goopg itself never noticed because goopg reads its catalogs without those
indexes.

Upstream has no such asymmetry, and for a structural reason worth recording:
`initdb` bootstraps template1 **in full** and only then makes template0 a
directory-level clone of it (`initdb.c` `make_template0` → `CREATE DATABASE
template0 … STRATEGY = file_copy`). A real cluster's `base/4` is byte-identical
to `base/1` apart from `pg_internal.init`, which the reference cluster at
`bench/tpch/runtime/pgdata` confirms (301 / 300 / 375 files for 1 / 4 / 5).

## The fix

`initdb.refreshTemplate0Image` (`internal/initdb/initdb.go`) re-clones `base/4`
from the finished `base/5` at the **end** of `Init`, after every bootstrapper
and after `bootstrapRelcacheInitFiles`, and before `stampClusterChecksums` (so
a `-k` cluster checksums the refreshed pages) and the trailing fsync. The early
`bootstrapPostgresDatabase` copy is left alone — nothing between the two points
depends on `base/4` being final, and leaving it in place keeps the change to
one additive function.

Two decisions worth their reasons:

- **Source is `base/5`, not `base/1`.** They are byte-identical for every file
  they share, but `base/5` additionally has `pg_filenode.map` and the
  per-database placeholder files for the shared-index OIDs — the exact extra set
  `base/4` already carried and must keep. Copying the superset guarantees no
  file in `base/4` is left older than its twin. (`base/1` has no
  `pg_filenode.map` at all in goopg — a separate deviation from upstream, noted
  in the deferral ledger.)
- **`pg_internal.init` IS copied**, unlike upstream's template0, which has
  none. goopg's relcache init file is generated by `bootstrapRelcacheInitFiles`
  and is what makes the hosted PG's `postgres` database work at all; a
  runtime-minted database is better off with the same one than with none. If
  this ever needs to change, the E2E below is the probe that would show it.

This answers S15.2 (mechanism: copy the template image, as upstream does, not
re-run the bootstrappers per database) and makes S15.1/S15.3 moot by
construction — the whole image is refreshed, so there is no critical-index
*set* to enumerate and get wrong. That is deliberate: the PANIC named one index,
but the same stale-ordering bug had left every populated file behind.

## Guards

- `internal/initdb/template0_image_test.go` —
  `TestTemplate0ImageMatchesPostgresDatabase`: whole-directory equality of
  `base/4` against `base/5` (PG_VERSION exempt), plus a size floor on `2662` so
  a future change that made both dirs equally *empty* could not slip through the
  equality. Proven fail-when-broken: with the refresh call removed it reports
  59 missing and 35 differing files.
- `internal/testport/e2e_pg_coldstart_on_goopgdata_test.go` — S15.4 inversion.
  `assertGoopgCreatedDatabaseStillUnopenableByPG` is replaced by
  `assertHostedPGReadsGoopgCreatedDatabase`, which asserts the hosted PG reads
  `s4other`'s row and reports a resurfaced `could not open critical system
  index` as a REGRESSION naming this doc's fix. The probe is no longer
  destructive, so Guard 4's log scan now covers the entire run; it stays in its
  place as the last probe regardless.

## Deferred

An **existing** `$PGDATA` initialised before this change keeps its stale
`base/4`, so databases created on it after upgrading still carry the empty
placeholders. There is no in-place upgrade step; `goopg init` is the only
producer of the image. Ledger row 2026-08-12.
