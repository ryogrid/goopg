# Review: 10-executor-pg-design.md + 12-executor-gap-analysis.md

Scope: read-only review of both docs. No reviewed file edited, no code
changed, no servers/tests. Method: full read of both docs; 30+ load-bearing
PG symbols re-checked via `global -x` + Read against `postgres/` oracle;
12's numbers re-checked against 11 §17, 07 §§2.1/4.1/6, and
`.ralph/deferral_ledger.md`.

## Verdict: APPROVE-WITH-CHANGES

Doc 10's citation discipline is excellent — every sampled `global -x`
symbol resolves at the cited file:line (dispatch, scans, joins, hash,
memoize, agg, sort, gather, tuplestore, expr, mcxt; full list in §V).

inflation, honors STALE/LANDED, and concedes where PG does the same thing.

false consumer attribution (F3) that the target design (13) must not build
on. Fix F1–F3, consider F4–F8, then land.

Finding counts: 2 major, 2 moderate, 4 minor/info. Doc 12: no blocking
finding; 2 nits (F9, F10) + 1 inherited-arithmetic note (F11).

## F1 [MAJOR] 10 §8 + §16: AGG_MIXED is not the hash-agg spill escape

- File/section: `10-executor-pg-design.md` §8 ("`MIXED` exists so `GROUP BY`
  with more groups than memory degrades into runs instead of dying in the
  hash table") and §16 table ("pure `HASHED` with more groups than memory
  is the pathology `AGG_MIXED` (sorted-run spill) exists to fix").
- Correct cite: `postgres/src/backend/executor/nodeAgg.c:134`
  ("an `AGG_MIXED` strategy that populates the hashtables during the first
  sorted phase") and `:159-168` (the "real node is marked `AGG_MIXED` if
  there are both types present" — i.e. hashed grouping sets chained with
  sorted/plain phases). `MIXED` is the **grouping-sets** strategy, not a
  memory-overflow mode.
- The actual PG 18 hash-agg spill is a separate partitioned
  logical-tape mechanism: `postgres/src/backend/executor/nodeAgg.c:200-211`
  ("we enter 'spill mode' … spill them to disk … partitioned …
  Spilled data is written to logical tapes", "see
  `hash_agg_check_limits()`"), which doc 10 never mentions.
- Suggested fix: rewrite the `MIXED` gloss as grouping-sets mixing
  (hashed sets in phase 0 + sorted phases 1..n); add a spill row for
  `hash_agg_check_limits` partitioned-tape spill; correct the §16
  "hashed agg" row accordingly.

## F2 [MAJOR] 10 §10: SharedTuplestore is parallel-hash infrastructure, not GatherMerge exchange

- File/section: `10-executor-pg-design.md` §10 ("Order-preserving exchange
  stages through `SharedTuplestore` … read via `sts_begin_parallel_scan`
  — one writer per worker, coordinated leader-side readers").
- Correct cite: `postgres/src/backend/executor/nodeGatherMerge.c:21`
  (`#include "lib/binaryheap.h"`), `:430-431`
  (`gm_heap = binaryheap_allocate(…)`), `:567-578`
  (`binaryheap_first/replace_first/remove_first`) — the leader merges
  worker heads with a **binary heap over per-worker tuple queues**, not a
  shared tuplestore. Every `sts_begin_parallel_scan` caller outside
  `sharedtuplestore.c` is parallel hash:
  `postgres/src/backend/executor/nodeHash.c:1526-1527` (repartition scan),
  `postgres/src/backend/executor/nodeHashjoin.c:1328,1357`
  (batch inner/outer scans); writers are `sts_puttuple` at
  `nodeHash.c:1474,1889`. (`struct SharedTuplestore` itself at
  `postgres/src/backend/utils/sort/sharedtuplestore.c:59` is cited
  correctly — only its attribution to GatherMerge is wrong.)
- Suggested fix: move the SharedTuplestore paragraph to the parallel-hash
  discussion (§6 tail); describe GatherMerge as tuple queues + binary
  heap (`heap_compare_slots`, `:752`).

## F3 [MODERATE] 10 §11: Memoize is not a tuplestore consumer

- File/section: `10-executor-pg-design.md` §11 consumers list
  ("`Memoize` overflow").
- Correct cite: `grep tuplestore nodeMemoize.c` returns **zero** hits in
  `postgres/src/backend/executor/nodeMemoize.c`. Oversized/pressured
  entries are handled in memory: LRU eviction (`:444-510`,
  `lru_list`), then whole-scan `MEMO_CACHE_BYPASS_MODE` (`:81`,
  `:806-823`, `:896-907`) — never a disk spill.
- Suggested fix: delete "`Memoize` overflow" from the consumer list
  (WindowAgg `:862,1077`, CTE scans, Material, SetOp/RecursiveUnion,
  portals stay).

## F4 [MODERATE] 10 §6: skew keys are planner-supplied MCVs, not "detected during build"

- File/section: `10-executor-pg-design.md` §6 ("Skew is pinned resident:
  `ExecHashSkewTableInsert` promotes hot keys detected during build").
- Correct cite: `postgres/src/backend/executor/nodeHash.c:452-480`
  (`ExecChooseHashTableSize(rows, …, node->skewTable, …, &num_skew_mcvs)`),
  `:633-638` (`ExecHashBuildSkewHash(state, hashtable, node,
  num_skew_mcvs)`). Skew buckets come from the planner's `skewTable`
  (MCVs); the executor pins them (`ExecHashSkewTableInsert`, `:2601`;
  probe-side check `:181-187`), it does not detect them.
- Suggested fix: "pins planner-supplied MCV keys resident via the skew
  table". Note doc 12 §9 already frames this correctly ("pinned resident
  by the MCV skew table (10 §6)") — doc 12 is more accurate than its
  upstream here; align doc 10 to it.

## F5 [MINOR] 10 §7: "single-key bypass" misstates Memoize bypass granularity

- File/section: `10-executor-pg-design.md` §7 ("Eviction is LRU over
  entries with a single-key bypass — oversized entries fall back to
  re-scanning").
- Correct cite: `postgres/src/backend/executor/nodeMemoize.c:806-823`
  (entry==NULL or `cache_store_tuple` failure → `mstatus =
  MEMO_CACHE_BYPASS_MODE` "until the end of the scan"), `:896-907`
  (same on fill-path overflow), `:914+` (bypass streams the inner plan
  directly). Bypass is per-scan under memory pressure, not per-key; and
  the LRU/entry-complete/single-row mechanics (`:78`, `:832`,
  `:764-768`) are otherwise described correctly.
- Suggested fix: "…with whole-scan bypass: entries that cannot be created
  or stored fall into `MEMO_CACHE_BYPASS_MODE` to end of scan."

## F6 [MINOR] 10 §9: bound pushdown omits the ExecSetTupleBound intermediary

- File/section: `10-executor-pg-design.md` §9 ("`tuplesort_set_bound`
  … pushed down from `ExecInitLimit`, `nodeLimit.c:447`").
- Correct cite: `postgres/src/backend/executor/nodeLimit.c:419-423`
  (`ExecInitLimit` calls `ExecSetTupleBound(compute_tuples_needed(node),
  …)`), `postgres/src/backend/executor/execProcnode.c:847-877`
  (`ExecSetTupleBound` sets `SortState->bounded/bound`), then
  `postgres/src/backend/executor/nodeSort.c:123-124` (`ExecSort` calls
  `tuplesort_set_bound`). The cited line 447 is the `ExecInitLimit`
  definition, not the pushdown call; the mechanism has one more hop.
  (`tuplesort.c:849-851` leader-ignores-hint and §16's "parallel leader
  ignores the bound" verified correct.)
- Suggested fix: cite the chain `ExecInitLimit → ExecSetTupleBound
  (execProcnode.c:848) → SortState.bounded/bound → tuplesort_set_bound`.
