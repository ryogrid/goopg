## 1. [MAJOR] Bitmap-lossy `maxentries` formula is wrong (02 §3.5, §9 item 24)

- File+section: `02-pg-cost-model.md` §3.5 ("`maxentries =
  work_mem*1024/64`") and §9 item 24 (same formula).
- What is wrong: the planner never divides by 64. `compute_bitmap_pages`
  (`postgres/src/backend/optimizer/path/costsize.c:compute_bitmap_pages`,
  line 6514, `global`-verified) computes (line 6555)
  `maxentries = tbm_calculate_entries(work_mem * (Size) 1024)`, and
  `tbm_calculate_entries`
  (`postgres/src/backend/nodes/tidbitmap.c`, line 1545, `global`-verified)
  returns `maxbytes / (sizeof(PagetableEntry) + sizeof(Pointer) +
  sizeof(Pointer))`. `PagetableEntry` (`tidbitmap.c:91`) embeds a full
  page/chunk bitmap (`words[]`), so the divisor is ~104 bytes, not 64 —
  the doc overestimates lossy-bitmap capacity by ~1.6x, which moves the
  exact→lossy threshold and `tuples_fetched`. The companion claim
  `lossy = max(0, heap − maxentries/2)` is correct (costsize.c:6589).
  The citation "(costsize.c:6580, tidbitmap.c)" also points at the wrong
  line: 6580 is inside the `lossy_pages` block; `maxentries` is set at
  6555.
- Suggested fix: replace both occurrences with "`maxentries =
  tbm_calculate_entries(work_mem*1024)` (costsize.c:6555;
  nodes/tidbitmap.c:1545; divisor is `sizeof(PagetableEntry)+2*ptr`,
  not 64)" and re-derive any downstream lossy-page arithmetic.

## 4. [MINOR] `isdefault` exclusivity claim is false (03 §4.1)

- File+section: `03-pg-statistics-infrastructure.md` §4.1 ("`rel ==
  NULL` or `ntuples ≤ 0` → 200 default (`isdefault = true` only in this
  arm)").
- What is wrong: `get_variable_numdistinct`
  (`postgres/src/backend/utils/adt/selfuncs.c`, line 6258,
  `global`-verified) sets `*isdefault = true` in three arms, not one:
  `rel == NULL` (selfuncs.c:6352), `ntuples <= 0` (selfuncs.c:6358),
  and the `ntuples >= DEFAULT_NUM_DISTINCT` no-data fallback
  (selfuncs.c:6376–6377) — all confirmed by Read. This also tensions
  §8.1, which correctly states the general rule
  ("`SELFLAG_USED_DEFAULT` set … when a default nd was used").
- Suggested fix: delete "only in this arm"; say "`isdefault=true` in
  all three default arms (NULL rel, non-positive tuples, and
  large-relation no-data fallback)".

## 5. [MINOR] Checklist `numIndexPages` drops selectivity/SA/clamp (02 §9 item 21 vs §3.3)

- File+section: `02-pg-cost-model.md` §9 item 21 ("`numIndexPages =
  ceil(tuples×pages/index.tuples)`") contradicting the correct §3.3.
- What is wrong: `genericcostestimate`
  (`postgres/src/backend/utils/adt/selfuncs.c`, line 7051,
  `global`-verified) computes `numIndexTuples =
  rint(indexSelectivity * rel->tuples / num_sa_scans)` (selfuncs.c:7119–
  7128), clamps to `[1, index->tuples]` (7136–7139), then
  `numIndexPages = ceil(numIndexTuples * index->pages / index->tuples)`
  with a `pages>1 && tuples>1` guard else `1.0` (7153–7156) — all
  confirmed by Read. The checklist drops the selectivity factor, the
  SA-scan division, the clamp, and the guard.
- Suggested fix: align item 21 with §3.3 (selectivity-scaled,
  SA-divided, clamped tuples; guarded pages).

## 6. [MINOR] Checklist TID-range drops selectivity (02 §9 item 26 vs §3.6)

- File+section: `02-pg-cost-model.md` §9 item 26 ("TID-range = random +
  seq×(pages-1)") vs §3.6.
- What is wrong: `cost_tidrangescan`
  (`postgres/src/backend/optimizer/path/costsize.c`, line 1363,
  `global`-verified) sets `pages = ceil(selectivity * baserel->pages)`
  (floored at 1) and charges random + seq×(pages−1). §3.6 states this
  correctly; the checklist's bare "`pages−1`" loses the selectivity
  scaling.
- Suggested fix: change item 26 to "random + seq×(ceil(sel×pages)−1),
  min 1 page".

## 8. [MINOR] `clamp_width_est` "never negative" overstates the code (02 §2.1)

- File+section: `02-pg-cost-model.md` §2.1 ("`clamp_width_est(w)`:
  min(w, MaxAllocSize), never negative").
- What is wrong: `clamp_width_est`
  (`postgres/src/backend/optimizer/path/costsize.c`, line 242,
  `global`-verified) caps at `MaxAllocSize` but handles negatives with
  `Assert(tuple_width >= 0)` only (costsize.c:254, confirmed by Read) —
  compiled out in release builds, where a negative passes through the
  cast. It is not a clamp on the low end, unlike `clamp_row_est`
  (costsize.c:213, `global`-verified), which forces ≥ 1.0.
- Suggested fix: "caps at MaxAllocSize; negativity is Assert-only, not
  clamped".
