## 2. Approved core decision: direct AST construction

goyacc semantic actions construct the **existing** goopg AST structs directly.
There is no intermediate "raw parse tree" node family and no conversion layer.

Rationale (user-approved 2026-08-25):

* A raw-tree + conversion layer would duplicate ~165 node types and add a
  multi-thousand-line conversion body with zero user-visible benefit.
* Direct construction keeps executor/optimizer/postmaster untouched — the
  migration surface stays inside the parser boundary.
* The concept sketch's "Raw Parse Tree" stage maps to what actually happens:
  yacc builds nodes incrementally on its value stack as productions reduce;
  there is simply no *second* representation afterwards.

Consequence: `%union` fields hold `*parser.XStmt` / `parser.Expr` / slices of
those, so the generated package must be able to reference `internal/parser`
types without an import cycle (see §5).

## 3. Target component layout

```
grammar/
  pg_grammar.y        # faithful port of postgres/src/backend/parser/gram.y,
                      # rules named identically; every rule block cites its
                      # upstream line range
  goopg_ext.y         # goopg-only syntax extensions, each tagged GOOPG-EXT;
                      # empty at first; kept separate from the PG-derived file
internal/sqlparser/   # NEW transitional package (migration home)
  yy_lex.go           # yyLexer adapter feeding the existing lexer to goyacc
  base_yylex.go       # port of PG's lookahead filter (parser.c base_yylex):
                      # _LA token substitutions (WITH/NOT/NULLS/FORMAT/
                      # WITHOUT) + UESCAPE triple handling. NOTE: keyword
                      # CATEGORY enforcement is grammatical (see 02 §4),
                      # not lexical.
  support.go          # action helpers too big for inline actions
  keywords_gen.go     # GENERATED by cmd/gen-kwlist-go (tokens + categories)
  <name>.go           # GENERATED by goyacc from concatenated grammar
cmd/gen-kwlist-go/    # generator: kwlist.h -> keywords_gen.go
```

Build integration mirrors the existing `cmd/gen-*` + Makefile pattern:

```make
gen-parser:                       ## regenerate LALR parser from grammar/
	go run ./cmd/gen-kwlist-go > internal/sqlparser/keywords_gen.go
	cat grammar/header.y grammar/pg_grammar.y grammar/goopg_ext.y \
	    > $(BUILD_DIR)/goopg_grammar.y
	cd internal/sqlparser && goyacc -o yacc_parser.go -v y.output $(BUILD_DIR)/goopg_grammar.y
	! grep -q 'conflicts:' internal/sqlparser/y.output   # MANDATORY conflict gate
```

* `grammar/header.y` carries the `%{ package sqlparser … %}` prologue
  (goyacc copies the preamble verbatim — no post-fixups needed).
* The **conflict gate is load-bearing**: goyacc exits 0 even with conflicts,
  so the grep FAIL is the only thing standing in for upstream's `%expect 0`
  (02 §6, 05-risks #1).

Generated `.go` files are committed to the repo (same policy as other
generated artifacts here); contributors only edit `grammar/*.y` and rerun
`make gen-parser`.

## 4. Lexer strategy: adapt, don't rewrite

The existing hand-written lexer already produces the right token stream shape
(`Token{Kind, Keyword, Value, Pos}`) and handles operators, `$n` parameters,
string/byte/hex literals and comments. It becomes the front half of the
`yyLexer` implementation:

* identifier that matches kwlist → generated keyword token (with category),
* everything else maps onto gram.y's terminal names (IDENT, FCONST, SCONST,
  BCONST, XCONST, Op, PARAM, ICONST, ...).
* `Pos` (byte offset) flows into yacc locations so error reporting keeps the
  current byte-position fidelity consumed by libpq ErrorResponse fields.

Known divergences between our lexer and scan.l are cataloged in 05-risks.md
and get closed during P0 rather than discovered mid-P1.

## 5. Import-cycle avoidance

`internal/sqlparser` needs `internal/parser` types (direct AST build), but
during migration `internal/parser.Parse()` must call `internal/sqlparser`
for routed statements → cycle if both directions exist.

Resolution:

* Phase P0..P6: `internal/sqlparser` imports `internal/parser`
  (one direction only). The **dispatch lives outside both** — see
  03-strangler-migration.md §2 for where Parse() routing actually sits.
* Cutover (P7): generated sources move INTO `internal/parser`; the
  transitional package is deleted. Final state: `internal/parser` contains
  lexer + keywords_gen + yacc_parser + ast + analyzer. External import paths
  never change.

## 6. Error reporting contract

Preserved verbatim from today:

* byte offset of the offending token → `Position` field on ErrorResponse,
* SQLSTATE 42601 via the existing message/SQLSTATE formatting path,
* PG-style message wording ("syntax error at or near \"x\"") including the
  M0134-0070 raw-source echo behavior — the port must not regress it.

Layering note: the `syntaxErrorMsg`/`syntaxErrorCode` helpers currently live
in `internal/postmaster` (dispatch.go, copy.go). Since `internal/sqlparser`
must not import postmaster, P0 relocates those helpers into
`internal/parser` (leaf position) with postmaster consuming them from there —
behavior-preserving move, one commit (TODO P0.x).

goyacc's default `yyerror` is replaced by a shim that formats through that
machinery using the current lookahead location.

## 7. What does NOT change

* `internal/parser/analyzer`, planner, executor, catalog — untouched.
* Public entry points keep their signatures: `Parse(input string,
  mc ...*mmgr.Context) ([]Stmt, error)` and `ParseExpr(...)`. mmgr contexts
  thread through the yacc stack via union fields where nodes need them
  (05-risks.md §3).
* plpgsql keeps its own recursive-descent parser; we only guarantee we do not
  break what it imports from `internal/parser`.
