## Problem

HammerDB's TPC-H Q15 (`HammerDB/src/postgresql/pgolap.tcl`
line ~996) builds a temporary view:

```
CREATE OR REPLACE VIEW revenue$<position> (supplier_no, total_revenue)
  AS SELECT l_suppkey, sum(l_extendedprice * (1 - l_discount))
       FROM lineitem
       WHERE l_shipdate >= … AND l_shipdate < …
       GROUP BY l_suppkey;
SELECT s_suppkey, …, total_revenue
  FROM supplier, revenue$<position>
  WHERE s_suppkey = supplier_no
    AND total_revenue = (SELECT max(total_revenue) FROM revenue$<position>)
  ORDER BY s_suppkey;
DROP VIEW revenue$<position>;
```

Without view support, Q15 can't run.

## Decisions

### View as substituted plan node, not catalog rewrite

Upstream PG stores views in `pg_class` / `pg_rewrite` and
expands them at the query-rewrite stage by replacing the
range-table entry with a subquery. v0 takes a simpler shape:
the catalog stores the view's parser AST, and
`planScanRangeVar` plans it recursively at every reference.

Pros:
- Single point of expansion — the planner doesn't need a
  separate rewrite phase.
- View definition is always re-planned against the live
  catalog, so changes to underlying tables (added columns,
  dropped indexes) take effect immediately.

Cons:
- No plan caching across queries that reference the same
  view. Each reference re-runs `Plan()` on the inner SELECT.
  For TPC-H Q15 the view is referenced twice (the outer
  query and the scalar subquery in WHERE), so the inner
  SELECT is planned twice. Performance optimisation, not
  correctness.

### Catalog: View flag + parser AST + alias list

`catalog.Table` gained two view-specific fields:

```go
View              *parser.SelectStmt   // view body
ViewColumnAliases []string              // optional column-name list
```

When `View != nil`, the table is treated as virtual: there's
no heap relation, no SeqScan, no DML allowed. `Virtual` stays
true on view rows so storage operators (Pool, smgr) keep
ignoring them.

`(*InMemory).CreateView` and `DropView` are the new public
APIs. `CreateView` honours `OR REPLACE` by deleting any
existing same-name view first; CREATE without REPLACE over
an existing object reports `relation … already exists`
(SQLSTATE 42P07).

### Column-name derivation: alias > target alias > target shape

`execCreateView` derives the view's catalog `Columns` from
three sources in priority order:

1. The explicit `( col_list )` after the view name.
2. The target's `AS alias`.
3. `deriveTargetName(expr)` — bare `ColumnRef` returns its
   column name, `FuncCall` returns the function name (matches
   upstream's "sum" / "count" convention). Anything else
   becomes `?column?N`.

Column types are recorded as `unknown` because v0 doesn't
re-run the type system at DDL time. The planner's
`planScanRangeVar` overrides each column's type with the
inner plan's `Output()` schema at every reference, so
downstream comparisons see the inferred type.

### Planner: planScanRangeVar substitutes the inner plan

The substitution checks `tbl.View != nil` first and recurses
into `Plan(tbl.View, cat)`. The returned node's column count
must match the catalog's; mismatches surface as 42P10 errors.

The outer resolve context's schema is rebuilt to combine the
view's column names (for downstream name resolution) with the
inner plan's column types (for downstream comparisons).

`planSelect`'s `isSimpleSingle` fast-path used to bypass
`planScanRangeVar` and call `buildVirtualValues` directly for
any virtual table. That path now delegates to
`planScanRangeVar` so view substitution lives in exactly one
place.

### What's NOT supported

- INSERT / UPDATE / DELETE on views. The planner produces a
  read-only plan node; DML against a view triggers an
  executor error because the substituted node isn't a
  storage operator. Updatable views (the `INSTEAD OF`
  trigger machinery in upstream) wait on the rule system.
- Recursive views (`CREATE RECURSIVE VIEW`). Not used by
  TPC-H.
- View persistence across server restart. The catalog
  snapshot doesn't yet serialise the view's parser AST;
  views vanish on restart. HammerDB workflows that
  CREATE+USE+DROP within a single session work fine.
- Column-name validation at DDL time — mismatched alias
  count is caught at first reference, not creation.

## Verification

End-to-end against `goopg start -D <dir>` with upstream psql
18.3:

```
CREATE TABLE lineitem (l_suppkey INT, l_extendedprice INT);
INSERT INTO lineitem VALUES (1,100),(1,200),(2,300),(2,400);

CREATE VIEW revenue (supplier_no, total_revenue) AS
  SELECT l_suppkey, sum(l_extendedprice)
    FROM lineitem GROUP BY l_suppkey;

SELECT supplier_no, total_revenue FROM revenue ORDER BY supplier_no;
-- (1, 300), (2, 700)

-- Q15-shape: scalar subquery against the view
SELECT supplier_no, total_revenue FROM revenue
  WHERE total_revenue = (SELECT max(total_revenue) FROM revenue);
-- (2, 700)

CREATE OR REPLACE VIEW revenue (sno, total) AS
  SELECT l_suppkey, sum(l_extendedprice)
    FROM lineitem GROUP BY l_suppkey;

SELECT sno, total FROM revenue;
-- column-rename works through OR REPLACE

DROP VIEW revenue;
DROP VIEW IF EXISTS revenue;  -- second DROP no-op via IF EXISTS
```

Tests: `TestParseCreateViewWithExplicitColumns` and
`TestParseDropViewIfExists` pin the AST shapes.

## Out of scope (deferred to subsequent loops)

- DML on views (INSERT/UPDATE/DELETE).
- Catalog persistence (views surviving server restart).
- View-with-CHECK-OPTION semantics.
- Recursive views.
- Materialised views (a different upstream subsystem).
- Plan caching across view references.
