# 0057-0004 — Crash Recovery Verification (kill -KILL)

| field      | value |
|------------|-------|
| status     | draft |
| date       | 2026-05-06 |

## 1. Problem

During the M0054-0007 benchmark runs, a kill -KILL of the goopg
process during an in-flight query (Q9 in run-014) left the data
directory in a state that required a full --reset reload. A SIGKILL
cannot be caught or handled; recovery must work from WAL replay alone.

Crash recovery from SIGKILL is a minimum requirement for any RDBMS.
Without it, any unexpected process exit (OOM killer, system crash,
developer Ctrl-C) results in data loss.

## 2. What crash recovery must provide

1. **Server starts without manual intervention** after kill -KILL.
2. **All committed rows are present** (SELECT count(*) on all tables
   returns the correct values from before the crash).
3. **No WAL replay ERRORs** in the startup log.
4. **Aborted transactions are rolled back** (partially-written rows
   are not visible).

The WAL replay path in goopg must:
- Read the WAL from the last checkpoint LSN.
- Apply INSERT / UPDATE / DELETE records in order.
- Handle all record types that can be generated by a normal SF=1
  schema-build + power-test run.

## 3. Test approach

### 3.1 Automated test (M0057-0005)

`TestKillKillRecovery` in `internal/testutil/cluster/`:

```go
// 1. Spin up cluster, create test table, insert N rows, COMMIT.
// 2. Begin a long transaction, insert more rows, do NOT commit.
// 3. Start a long-running SELECT on a background connection.
// 4. Send SIGKILL to the goopg process.
// 5. Wait for process to die.
// 6. Restart cluster with cluster.Start().
// 7. Assert server starts cleanly (no error in startup log).
// 8. Assert committed rows (from step 1) are all present.
// 9. Assert uncommitted rows (from step 2) are NOT visible.
```

### 3.2 Manual SF=1 test

After loading SF=1 and running Q9 for ~30 seconds:
```
kill -9 <goopg-pid>
./tmp/goopg-bench-bin start -D bench/tpch/runtime_goopg/data ...
# verify tables:
./tpch-runner --queries=2 --per-query-timeout=60s
```
Document the result in `analysis/0057-crash-recovery-test.md`.

## 4. If recovery fails

If the automated or manual test fails, the WAL redo path has a bug.
Common failure modes and investigation starting points:

| Symptom | Likely cause |
|---------|-------------|
| Server panics on startup | Missing WAL record type in replay switch |
| Missing committed rows | Checkpoint LSN not advanced correctly; replay stops too early |
| Server hangs on startup | Infinite loop in WAL replay |
| Extra rows visible | Uncommitted transaction replay not rolled back |
| Page checksum mismatch | FPI (full-page image) not replayed correctly |

**Do NOT defer if the test fails.** Fix the WAL redo path before
closing M0057-0005.
