# M0138-0001 — ANALYZE divergence census

Status: accepted (landed 2026-09-15)

## Task

Recon task, no production change (per `AGENT.md` §"Plan-parity harness" —
`M0138-0001` is one of the three named recon tasks). Measure and record
exactly where goopg's `ANALYZE` diverges from PG 18.3's `acquire_sample_rows`
(`postgres/src/backend/commands/analyze.c:1199`), and produce a per-column
divergence table over both corpora (TPC-H SF=1, TPC-DS SF=0.25).

## Method

Live capture against the four standing bench clusters (`CLAUDE.md`'s table):
goopg TPC-H `:65433` (already-loaded `bench/tpch/runtime_goopg/data`, started
this task via `bench/tpch/setup_goopg.sh` — idempotent, no `--reset`, did not
touch the data), PG TPC-H reference `:65432`, goopg TPC-DS SF0.25 `:65437`
(started via `bench/tpcds/server.sh start sf025`), PG TPC-DS reference
`:65438` (db `tpcds025`). All four are left running afterward — they are the
shared `:6543x` lane, not throwaway clusters (AGENT.md "Server traps": verify
a reference, never restart it).

Both goopg clusters were `ANALYZE`d fresh in the querying session (goopg's
statistics are per-connection, M0137-0003 §2), then `pg_stats` was read for a
representative column set: all of TPC-H's eight tables (61 columns) and
TPC-DS's `customer`/`date_dim`/`store`/`item`/`store_sales` (121 columns,
`store_sales` being the large fact table — the shape most exposed to the
block-representation gap). Raw captures: `/tmp/m0138-census/{goopg,pg}_{tpch,tpcds}_cols.txt`
(scratch, not committed — same precedent as M0137-0002/-0003's manual
verification captures).

**Caveat on absolute-value comparisons.** TPC-H's two corpora are
independently generated by HammerDB client-side per engine (`CLAUDE.md`,
`hammerdb_tpch_integer_keys_are_numeric` memory) — row counts differ
slightly between goopg's and PG's `lineitem` (goopg `l_comment` ndistinct
133,080 vs PG's 145,256, i.e. not byte-identical populations). Absolute
`n_distinct`/`correlation` values are therefore not expected to match
exactly even under a perfect port; what is comparable and meaningful is
**sign, order of magnitude, and structural pattern** (unique vs non-unique,
scattered vs banded). TPC-DS's SF0.25 load is the same TPC-DS generator on
both engines and is a tighter comparison.

## Confirmed: the milestone doc's named divergence (block representation)

Already-cited and unchanged by this task; live-reconfirmed by source read:

- goopg (`operators_analyze.go:835`, `analyzeRelationWith`) scans **every
  block** (`for blk := 0; blk < nBlocks; blk++`) and reservoir-samples over
  every visible row (classic Algorithm R: one `rng.Int63n(seen+1)` draw per
  row past the cap).
- PG (`analyze.c:1199` `acquire_sample_rows`) first selects up to `targrows`
  **blocks** via `BlockSampler_Init`/`_Next` (`sampling.c:39,64`, Knuth
  Algorithm S) — for a relation with `totalblocks <= targrows` this degrades
  to "select every block" (`Min(bs->n, bs->N)`, `sampling.c:53`), which is
  exactly why the TPC-DS SF0.25 `customer` table (fits inside
  `targrows=30000` at `stats_target=100`) shows near-identical `n_distinct`
  between engines (`c_birth_country` 211/211, `c_first_sales_date_sk`
  3650/3650, `c_current_hdemo_sk` 7166/7129) while `lineitem`/`store_sales`
  (far larger than `targrows`) do not. Then within the sampled blocks, PG
  runs Vitter's Algorithm Z (`reservoir_get_next_S` + `sampler_random_fract`,
  `analyze.c:1228-1290`) — a *skip-count* reservoir, statistically equivalent
  to Algorithm R but drawing from a **different population** (only rows on
  sampled blocks, vs goopg's every row).

## New: three divergences not named in the milestone doc

### 1. `RowCount`/`reltuples` — goopg exact, PG's is a sample-extrapolated estimate

goopg's per-table `RowCount` (`operators_analyze.go:32-34`, `873`) is an
exact count: every block is visited, every tuple's visibility is checked.
PG's `*totalrows` (`analyze.c:1330-1339`) is **never exact once
`totalblocks > targrows`** — it extrapolates from only the sampled blocks:

```c
*totalrows = floor((liverows / bs.m) * totalblocks + 0.5);
```

(`bs.m` = blocks actually sampled, `liverows` = live rows seen on those
blocks.) This is a distinct divergence from the per-column block-sampling
gap above: it means `pg_class.reltuples` itself is a random variable in PG
(varies run to run, even against static data, whenever `bs.m < totalblocks`)
while goopg's `RowCount` is deterministic. `reltuples`/`RowCount` feeds
nearly every row-count-based cost estimate, so this is corpus-wide, not
column-specific. **Not addressed by M0138-0002's per-column focus as
scoped** — flagged as a scope question for that task (does "port the block
sampler" include switching `RowCount` itself to the extrapolated estimate,
given goopg's exact count is also relied on outside planning, e.g. `VACUUM`
reporting?). Ledger row filed.

### 2. Correlation: PG breaks ties by original physical position; goopg's tie order is unspecified

PG's `compute_scalar_stats` (`analyze.c:2438-2550`) sorts the sample by
value using `qsort_interruptible` with `compare_scalars`
(`analyze.c:2931-2950`), which threads a `tupnoLink[]` array: when two
values compare equal, `compare_scalars` records the tie but the **sort
itself is deterministic in tie order** — ties are effectively ordered by
`tupno` (the original, physical-scan-order sample index), because
`values[i].tupno` was assigned in physical-scan order before the sort and
the comparator's only tie input is `ta`/`tb` (the tupnos) themselves,
consulted the same way every time. `corr_xysum` (`analyze.c:2540-2545`) is
then accumulated over `(sorted_rank, tupno)` pairs — a well-defined,
repeatable convention for the ambiguous case of tied values.

goopg's equivalent (`operators_analyze.go:1216-1247`) sorts `corrPairs` with
Go's `sort.Slice`, whose tie order is **explicitly unspecified** (not
required to be stable, and the stdlib's introsort does not preserve
relative order for equal keys). There is no tie-breaker in the `less`
closure — `compareDatum(...) < 0` returns `false` for equal values,
so `sort.Slice` is free to interleave tied entries however its
partitioning happens to fall.

**Live evidence this is not merely theoretical.** TPC-DS `store_sales`
(structurally the case most exposed — many low/mid-cardinality FK columns,
each with thousands of duplicate values): goopg's correlation for 12 of 23
columns falls inside a narrow, semantically-unrelated band
(`0.12`-`0.15` — `ss_addr_sk` 0.138, `ss_cdemo_sk` 0.138, `ss_hdemo_sk`
0.151, `ss_promo_sk` 0.131, `ss_quantity` 0.136, `ss_sales_price` 0.146,
`ss_sold_date_sk` 0.154, `ss_sold_time_sk` 0.129, `ss_wholesale_cost`
0.154, plus three more), while PG's values for the same columns scatter
near zero (`-0.0013` to `0.012`) with no such band. Corpus-wide count:
goopg has **36 of 118** TPC-DS columns landing in `[0.09, 0.16]`, PG has
**7 of 119** — a 5x over-representation. TPC-H (a flat, non-star schema
with far fewer heavily-duplicated FK-shaped columns) does not show the same
banding, consistent with the hypothesis (tie-order sensitivity should track
duplicate density, and TPC-DS's dimension FKs are exactly the
highest-duplicate-density columns in either corpus).

This is filed as a **hypothesis, not a confirmed root cause** — the band
could also stem from a genuine load-order artifact of the TPC-DS SF0.25
loader (shared surrogate-key generation pattern across FK columns) rather
than the sort itself. Distinguishing the two needs a controlled test (e.g.
force a stable tie order in goopg's sort against a synthetic table with
known ties and compare to a hand-computed PG-convention answer) — out of
scope for a no-code-change recon task. Resume point: M0138-0004 ("MCV,
histogram and correlation from the shared sample") is the right owner,
since it already re-derives correlation from PG's `compute_scalar_stats`
selection rule and will need `sort.Slice`'s tie order addressed either way
once ties are threaded through with tupno-equivalent tracking.

### 3. `pg_stats.avg_width`: no fixed-width `typlen` fallback for non-varlena columns

PG's `compute_scalar_stats`/`compute_distinct_stats`/the two `toowide`
short-circuit paths all set `stats->stawidth` one of two ways: sampled
average width for varlena/var-width columns, or the type's fixed `typlen`
otherwise — four call sites confirm the fallback (`analyze.c:2026`, `2206`,
`2381`, `2586`, `2902`, `2914`). goopg's per-column `AvgWidth`
(`computeColumnStats`, `operators_analyze.go:1191`) is computed **only**
from `datumVariablePayloadWidth` (`:1115-1130`), whose `switch` handles
`KindString`/`KindBytes`/`KindEnum` and `KindNumeric`'s big-numeric slow
path — every other `Datum.Kind` (int2/int4/int8/date/float4/float8/bool/
the numeric fast path when the mantissa fits `Datum.Int`, etc.) falls
through to `default: return 0`, and there is no fixed-`typlen` fallback
anywhere in the file (confirmed: `AvgWidth` is assigned in exactly two
places, `:925` for the unrelated table-level average and `:1191`).

**Live evidence.** 32 of 61 TPC-H columns and 70 of 121 TPC-DS columns
report `avg_width=0` in goopg's `pg_stats` where PG reports a positive
width — every `int4`/`int8`/`date`/`numeric`-fast-path column in both
corpora (e.g. TPC-H `c_custkey`, `l_orderkey`, `l_extendedprice`,
`l_shipdate`; TPC-DS every `_sk` surrogate key and every `numeric` money
column in `store_sales`). This is corpus-wide and independent of the
block-representation gap — it reproduces even on TPC-DS `customer` (a table
small enough that both engines scan every block). Unlike the correlation
finding above, this one has a definite, cheap, well-understood fix (typlen
fallback keyed off the column's catalog type, mirroring PG's four call
sites) with no tuning-toward-a-number risk — it is a clean parity gap, not
an estimation-error question. Resume point: M0138-0004, same selection-rule
pass, since `avg_width` is part of `compute_scalar_stats`'s output the same
sample-derived slot the correlation fix also touches.

## What was not done (scope boundary)

- No production code touched (recon task).
- Root cause of the correlation banding (finding 2) is not confirmed, only
  evidenced and hypothesized — see resume point above.
- `RowCount`/`reltuples` extrapolation (finding 1) is recorded as a scope
  question, not resolved — M0138-0002 must decide whether "port the block
  sampler" includes switching `RowCount` to PG's extrapolated form.
- `stadistinct` end-to-end verification (the milestone's M0138-0003) is out
  of this task's scope; this census only reconfirmed the existing R78
  witness pattern (goopg `l_orderkey` fractional `-0.1956` vs PG's absolute
  `358390` on the current TPC-H load — same sign/shape as R78's `-0.1956`
  vs `347537`, consistent with independent-load count drift, not a new
  divergence).
- `n_mcv`/`n_hist` slot-count comparison was captured (both columns of the
  raw tables) but not analyzed in depth — a first skim shows counts already
  close (`num_mcv`/`num_hist` both derive from `stats_target`, which is
  already faithfully ported), so it did not surface a new finding worth a
  dedicated section; left as raw evidence for M0138-0004 if needed.
