# 0100-0005k — Foreign-key violation error message matches PG shape

**Status:** accepted (2026-05-15)

## Problem

`internal/executor/operators_fk.go::assertParentExists` was emitting

```
insert or update on table "" violates foreign key constraint: key (a) not present in table "pk_noparted" (23503)
```

for every FK violation. The first `%q` slot was hard-coded as `""` (empty
string), and the tail of the message was a freeform sentence rather than the
upstream PG split where the constraint *name* lives on the MESSAGE line and the
unmatched *key/value* lives on the DETAIL line.

`fk-snapshot.spec` L21 carries the load-bearing form:

```
ERROR:  insert or update on table "fk_parted_pk_2" violates foreign key constraint "fk_parted_pk_a_fkey"
```

The empty-string slot caused every spec that exercises a parent-missing FK
violation (fk-snapshot.spec and a handful of partition-key-update specs that
chain inserts through a partitioned FK target) to diverge before any real
behaviour was observed. The downstream isolation runner's diff machinery
showed the L21 mismatch first, masking the more interesting wait-state and
serialise-error diffs.

## Fix

1. Thread the *referencing* table through to the error site.
   `assertParentExists(ctx, fk, vals)` becomes
   `assertParentExists(ctx, childTbl *catalog.Table, fk, vals)`; both callers
   (`checkFKInsert` and `fullTableFKCheck`) pass the table whose FK list was
   walked.
2. Synthesise the constraint name as `<table>_<col>_fkey` —
   upstream's `ChooseConstraintName` default for inline `col REFERENCES …`
   declarations. The catalog has no `Name` field on `ForeignKey` yet, so this
   is a one-arm rule: it matches PG's auto-generated case (the only case the
   isolation suite exercises). Named CONSTRAINT clauses are out of scope for
   this loop — the storage shape will need a `Name string` addition before the
   `fkConstraintName` helper can consult it.
3. Split MESSAGE and DETAIL the way libpq's `PQresultErrorField` exposes them:

   - MESSAGE: `insert or update on table "X" violates foreign key constraint "Y"`
   - DETAIL: `Key (col)=(val) is not present in table "Z".`

   `ExecError` already carries a `Detail` field (M0097-0003); the wire layer
   forwards it on the existing 'D' tag of `ErrorResponse`.

## Why this is the safe shape

- Partition routing in `insertOp.Next` happens *after* `checkFKInsert`, so the
  table threaded into the error is the parent partitioned table, not the
  routed child partition. Upstream PG reports the routed partition name
  (e.g. `fk_parted_pk_2`); we report the declaration site
  (`fk_parted_pk`). This is a *strictly better* signal than `""` and matches
  every non-partitioned spec exactly; the partition-routed name remains as
  follow-up scope. Moving the FK check past the routing site is a larger
  refactor than this loop targets — it changes when DEFAULT and trigger
  evaluation observe the row, and the deferred-FK queue's `ChildTableName`
  field would need to track the routed name too.
- The `fkConstraintName` helper is defensively nil-safe so callers that pass a
  nil table (defensive — none currently do) get `"_a_fkey"` rather than a
  panic.
- Value formatting in DETAIL uses `Datum.Format()` (already the wire-text
  formatter): integers as decimal, strings unquoted, NULL as `null`. PG quotes
  strings as `'foo'` inside the DETAIL parentheses, which we'll align if any
  spec surfaces a string-typed FK violation diff.

## Regression pins

`internal/executor/operators_fk_test.go`:

- `TestFKConstraintNameAutoGenerated` — `<table>_<col>_fkey` synthesis.
- `TestFKConstraintNameNilTable` — nil-safety.
- `TestFKValsForDetailFormatsInts` / `TestFKValsForDetailFormatsMixedTypes` —
  DETAIL value formatter.
- `TestFKViolationMessageMatchesPGShape` — byte-equal pin against the
  upstream fk-snapshot.spec L21 form.

## Out of scope (follow-up)

- Named CONSTRAINT clauses: add `Name string` to `catalog.ForeignKey`,
  populate it from `parseTableConstraint`, and prefer it in
  `fkConstraintName` when non-empty.
- Reporting the partition-child name in the MESSAGE for partitioned FK
  targets: move the FK check after partition routing (or do a second probe
  inside the partition branch). Required for full fk-snapshot pass — the spec
  expects `fk_parted_pk_2` (the partition child), not the declaring parent.
- String / numeric value quoting inside the DETAIL parentheses to match PG's
  `'foo'` / `1.23` exactly.
