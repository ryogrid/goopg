# M0106-0010 step 3db — pg_proc_oid_index populated 2-page btree

**Status:** Landed 2026-05-18
**Spec:** M0106-0010 (PG18 physical streaming replication: standby boot
catalog parity)
**Predecessor:** Step 3da (pg_type I/O regproc OIDs populated)
**Successor:** Step 3dc (still TBD; depends on the next standby pg.log
observation after 3db)

## Problem

After Step 3da landed canonical PG18 I/O regproc OIDs into every
bootstrapped `pg_type` heap row, the standby's `pg.log` showed:

- `cache lookup failed for type 23` — **0** lines (Step 3cz invariant
  still holds).
- `no output function available for type integer` — **0** lines (the
  metric Step 3da was scoped to drive to zero).
- `signal 11: Segmentation fault` — **1** lone surviving event, on a
  client backend during `InitPostgres` (postinit.c:723).

The crashing backend in the latest pre-3db capture (PID 1182375) did
exactly two AIO `shared_buffer_readv_cb` cycles, both completing OK
with `result 1` / `raw_result 8192` (one page each), and then sat for
~1s before the postmaster reaped it with SIGSEGV — no `ERROR`, no
`FATAL`, no `cache lookup failed for function …` preceded it.

The working hypothesis at the end of Step 3da, baked into
`.ralph/fix_plan.md`, was that the next gating dependency is a SysCache
miss on `PROCOID` (e.g. `int4out`=43): the I/O regproc OIDs are now
*encodable* in pg_type rows, but the corresponding pg_proc rows are
not yet *resolvable* via the indexed PROCOID path. Empirically, the
inspected `base/{1,5}/2690` file is the empty-btree placeholder
generated by the generic placeholder loop in `bootstrapSystemCatalogs`
— a metapage-only file with no leaf entries — so even the 7 AM
handler rows that `bootstrapPgProcTuples` writes to `base/{1,5}/1255`
are unreachable through the indexed path. PG18's
`SearchSysCache1(PROCOID, …)` would scan the empty btree, find no
leaf, return NULL, and any downstream `GETSTRUCT` deref would crash
without first producing an ereport message.

## Fix

1. `internal/initdb/initdb.go::bootstrapPgProcTuples` now returns
   `([]heapTID, error)` instead of just `error`, exposing the
   per-entry heap TIDs to its caller. (Step 3da uses the same shape
   for `bootstrapPgTypeTuples` → `bootstrapPgTypeOidIndex`.)
2. New `internal/initdb/btree_index_bootstrap.go::bootstrapPgProcOidIndex`
   mirrors `bootstrapPgTypeOidIndex` exactly: sort the 7 entries by
   OID, encode each as `pgBuildIndexTupleOidKey(block, off, oid)`,
   pack into a leaf-root page, prepend a metapage with
   `rootBlock=1, leafLevel=0`, and overwrite `base/{1,5}/2690`. No
   `global/` copy — `pg_proc` is per-database.
3. `bootstrapSystemCatalogs` in `internal/initdb/initdb.go` calls
   `bootstrapPgProcOidIndex(abs, pgProcTIDs)` immediately after
   `bootstrapPgProcTuples`, before `bootstrapPgOpclassTuples`.

The on-disk file is exactly `2 * BlockSize = 16384` bytes after the
overwrite, the leaf carries `len(pgProcInitialEntries()) == 7`
oid-keyed IndexTuples in strictly ascending OID order, and bthandler
(OID 330) — the canary every nailed btree index exercises during
`RelationInitIndexAccessInfo → OidFunctionCall0(amhandler)` — is
guaranteed to be present (covered by the new regression pin below).

## Why the placeholder loop is not enough

The existing OID list at `internal/initdb/initdb.go:832` enumerates
`2690` among the indexes that need an on-disk file (so that
`mdopen(base/{1,5}/2690)` succeeds), but the file it writes is a
**single-page metapage-only btree** — no leaf, no entries. PG can
open and read the metapage; what it *cannot* do is find any leaf
entry, so every `SearchSysCache1(PROCOID, …)` returns NULL. The
Step 3cw / 3cx / 3cz pattern explicitly upgrades the placeholder to
a populated 2-page btree (metapage + leaf-root) so the relevant
SysCache lookups resolve. Step 3db is the equivalent upgrade for
`pg_proc_oid_index`.

## Regression pin (new)

`internal/initdb/pg_proc_oid_index_test.go::TestBootstrapPgProcOidIndexWritesPopulatedBtree`:

- File size is exactly `2 * storage.BlockSize` on both
  `base/1/2690` and `base/5/2690`.
- Leaf `pd_lower` line-pointer count matches the number of pg_proc
  heap tuples (`len(tids)`).
- Every line pointer has a non-zero offset/length and the tuple
  payload lives within the page bounds.
- OIDs decoded from the IndexTuple key region are strictly ascending.
- **Mandatory** bthandler leaf — `gotOIDs` must contain `330`. This
  is the exact key whose absence would re-introduce the SIGSEGV
  during nailed btree index initialisation.
