# 0149-0016 — Port recovery/t/009\_twophase.pl

Status: in progress. The port is written and skipped unless `GOOPG_TAP_009=1`. Its all\-goopg run gets through the
restart, teardown, standby\-checkpoint and two "primary down" restores.

Upstream: `postgres/src/test/recovery/t/009_twophase.pl`; twophase.c \(`CheckPointTwoPhase`, `restoreTwoPhaseData`,
`StandbyRecoverPreparedTransactions`, `FinishPreparedTransaction`\), xlog.c \(`CreateRestartPoint`, `recoveryTargetTLI`\),
walsender.c `WalSndDone`, system\_views.sql `pg_prepared_xacts`.

## What the test checks

london and paris swap primary/standby roles three times, with synchronous replication in both directions. Prepared
transactions with savepoints must survive:
- clean and immediate restarts;
- replay on a running standby, with and without standby checkpoints;
- promotion;
- restart of a standby holding prepared state, once from state files and once from WAL records;
- a REPEATABLE READ snapshot on a hot standby;
- prepared DDL.

The last step drives pg\_subtrans traffic with pgbench.

## Fixed in this slice \(each a proven 009 blocker\)

- `subtransaction_buffers` was not a registered GUC, so goopg refused paris's postgresql.conf.
- `pg_prepared_xacts` now lists the prepared\-transaction registry: xid, gid, prepared\_at, owner and database, read
  from the state. Before, it was a zero\-row stub. `InMemory.SetVirtualRows` fills the built\-in stub.
- Restartpoints call `CheckPointTwoPhase(redo)` \(`CreateRestartPoint` → `CheckPointGuts`\), so a standby writes
  `pg_twophase` files too.
- `restoreTwoPhaseData` runs on a standby's startup too. There it only registers \(`StandbyRecoverPreparedTransactions`\);
  promotion assigns proc slots. It scans WAL from this node's own pg\_control redo \(on a standby, its last
  restartpoint\), not from the newest checkpoint record in the received WAL.
- Timelines:
  - A standby adopts the newest timeline its own pg\_wal carries at startup \(`xlog.LatestLocalTimeline`,
    recovery\_target\_timeline = latest\).
  - Promotion takes the timeline replay ended on \(`xlog.ReplayTimelineAt`\).
  - Without these, a standby restarted after streaming onto a newer timeline promoted from the older one. It copied
    the switch segment's prefix from the wrong file, and the next restart resumed WAL behind its standby.
- Finishing a restored prepared transaction waits for synchronous standbys \(`FinishPreparedTransaction` →
  `SyncRepWaitForLSN`\).
- `WalSndDone` sends a keepalive with reply\-requested, so a stopping primary gets the standby's flush at once instead
  of waiting up to its 10 s bound. Before, a fast stop could exceed a 10 s shutdown wait.
- tapnode gains `Pgbench`.

## 0016b — clog replay starts at this node's redo \(done\)

- Rows 23–24 \(and once 26\) vanished from a standby that was crash\-stopped and restarted. Cause:
  `replayCLogFromWAL` started at the newest checkpoint record in pg\_wal \(`ExportedReplayStart`\). On a standby that is
  the primary's checkpoint. It can come after the standby's own last restartpoint, the point up to which its clog was
  flushed.
- Commits replayed between the two \(in memory only\) were never re\-stamped, so the startup sweep marked them aborted.
  This happened for any commit, not just prepared ones: `TestE2E_StandbyCrashKeepsCommitsBeforePrimaryCheckpoint`
  loses even the CREATE TABLE at the old HEAD.
- The clog pass now starts at pg\_control's checkpoint redo when that comes earlier, as StartupXLOG replays from
  `checkPointCopy.redo`.

## 0016a — standby snapshots and finished\-prepared subtransactions \(done\)

- **Hot\-standby snapshots hold prepared xids as running.** While in recovery, `captureSnapshot` adds every registered
  prepared transaction's xid and subxids to the in\-progress list \(PG's KnownAssignedXids keeps prepared xacts until
  their finish replays\). A REPEATABLE READ snapshot taken before COMMIT PREPARED replays keeps seeing 0 rows.
  - It only shows when the standby was restarted while prepared: on a running standby, nextXid lags the prepared xid,
    so the snapshot already treats it as a future xid.
  - `TestE2E_HotStandbyOldSnapshotHidesLaterCommitPrepared` fails at the old HEAD.
- **Finishing a prepared transaction stamps its whole tree** \(`TransactionIdCommitTree` / `AbortTree` in
  `RecordTransactionCommitPrepared`\).
  - The finish record lists the children from the two\-phase state \(`TakeTwoPhaseEntry`, merged with any tracked
    live\).
  - Their clog status is set with the parent's. Before, only the top xid was stamped.
  - The children had been kept out of the startup sweep while prepared. Once a checkpoint passed the finish record, a
    restart swept them aborted: savepoint rows of restored prepared transactions vanished, intermittently in 009.
  - A read in between masked it, because it set hint bits.
  - `TestE2E_PreparedXactSurvivesRestart` \(no read before the checkpoint and crash restart\) fails at the old HEAD.

## 0016f — mixed pairings \(sync wait after PREPARE, truncated pivots\)

- **PREPARE TRANSACTION waits for synchronous standbys** \(`EndPrepare` → `SyncRepWaitForLSN`\). In the goopg\-london /
  PG\-paris pairing, london is crash\-stopped right after PREPARE. Without the wait, PG paris could miss the record and
  report "xact\_009\_10 does not exist" after promotion. That pairing now passes end to end.
- **Catalog btree descent handles PG's suffix\-truncated pivots.**
  - `pivotAwareCmp` reads `INDEX_ALT_TID_MASK` and the attribute count in the t\_tid offset \(`BTreeTupleGetNAtts`\).
    It compares the present attributes only; a key equal on them sorts after the pivot, as `_bt_compare` does.
  - Per\-index key layouts \(`sysBtreeKeyTypes`, plus the oidvector of `pg_proc_proname_args_nsp_index`\) cut the
    prefix at attribute boundaries.
- The PG\-london pairing was still blocked here by 0016e \(below\).

## 0016e / 0016g — CREATE TABLE on a goopg node promoted from a PG backup

- **cstring name keys \(0016e\).** PG's btree `name_ops` has `opckeytype = cstring`. The index attribute is typed
  cstring, and `index_form_tuple` stores a name key as its bytes plus a NUL, with `INDEX_VAR_MASK` set. goopg builds the
  same indexes with 64\-byte NameData keys typed `name` \(self\-consistent; see 0016j\).
  - `sys_catalog_btree_cstring.go` reads the layout off the index's leftmost leaf: on a fixed\-layout key,
    `INDEX_VAR_MASK` can only come from a cstring.
  - A cstring index gets goopg's new tuple re\-formed in the cstring layout, so a PG node reading the files later sees
    its own format. Every comparison \(leaf, split merge, pivot descent\) converts both operands back to NameData
    first.
  - Unit tests are pinned to the bytes of PG 18.3 initdb's `pg_class_relname_nsp_index` tuples.
  - PG 18.3, started on the promoted node's files, finds the goopg\-created table through that index and creates
    another one.
  - `pg_proc_proname_args_nsp_index` is held back. goopg's catalog does not know functions PG created, so
    `CREATE OR REPLACE FUNCTION` would add a duplicate pg\_proc row \(012 pg18\-primary regressed with it; 0015f\).
- **FSM block past EOF \(0016g\).** The heap insert's FSM candidate pick now does freespace.c
  `fsm_does_block_exist`: an entry past the relation's end is zeroed and skipped. The bad entry came from
  `ReadFSMFork` reading PG's root\-first FSM file as goopg's leaves\-first layout \(filed, 0016h\).
- Movement: the PG\-london pairing now fails only at the pg\_subtrans step, like all\-goopg.

## Still failing \(all\-goopg and PG\-london\)

- `pg_ls_dir` and `pg_stat_file` do not exist, and the pg\_subtrans step needs real pg\_subtrans files that change.

## Not covered

- Recovery snapshots hold only prepared xids as running. Ordinary in\-progress primary xids are judged by clog alone
  \(no KnownAssignedXids from RUNNING\_XACTS / XLOG\_XACT\_ASSIGNMENT\).

- `pg_prepared_xacts.prepared` is rendered in UTC, not the session time zone.
- `subtransaction_buffers` is accepted but sizes nothing. PG's `check_subtrans_buffers` rules are not enforced.
