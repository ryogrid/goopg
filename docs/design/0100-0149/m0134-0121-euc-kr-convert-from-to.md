# M0134-0121 — `euc_kr.sql`: `convert_from`/`convert_to` + EUC_KR↔UTF8 conversion

Status: **PASS** (1/1, 100% parity, byte-identical to the oracle).

## What the file tests

`postgres/src/test/regress/sql/euc_kr.sql` exercises `is_multibyte_char_in_char`'s
"slow path" (PG's substring-search fallback for non-UTF8, multibyte server
encodings): it decodes two `bytea` literals as EUC_KR via `convert_from`, then
runs `POSITION()` of the shorter decoded string inside the longer one. The
file self-skips (`\if :skip_test`) unless the *server* encoding is `EUC_KR` or
`UTF8` — goopg's server encoding is always `UTF8`, so the file always runs the
real assertion (`expected/euc_kr.out`, not the `_1.out` self-skip variant).

## Root cause: `convert_from`/`convert_to` did not exist at all

`SELECT convert_from('\xbcf6c7d0', 'EUC_KR')` returned `function convert_from
does not exist` — the function was registered in `pg_proc`
(`internal/initdb/pg_proc_seed_data.go`, OID 1714/1717, `HandlerName:
"pg_convert_from"`/`"pg_convert_to"`) but `internal/executor/expr.go`'s
function-call dispatch had no `case` for either name, so the seeded catalog
row was reachable by lookup/`\df` but never actually callable — a
declared-but-undispatched builtin, distinct from the "stub returns NULL"
pattern seen elsewhere (e.g. `LANGUAGE C`, M0134-0120).

Fixing dispatch alone was not enough: even with a `convert_from`/`convert_to`
case wired to `internal/utils/mb.DoEncodingConversion` (the existing
conversion-proc dispatcher, already used by COPY and
`maybeConvertCellsForClientEncoding` for `client_encoding` transcoding), no
EUC_KR↔UTF8 `ConvProc` was registered — only LATIN1, LATIN2, and (structural-
only, M0134-0107) EUC_JP existed in `internal/utils/mb`.

## The EUC_JP precedent does not apply here

`internal/utils/mb/euc_jp.go` (M0134-0107) deliberately stops at *structural*
validation (`pg_eucjp_verifychar`'s grammar rules) and reports any
structurally-valid non-ASCII character as `ErrUntranslatableChar`, because
porting PG's real JIS X 0208/0212 → Unicode table
(`postgres/src/backend/utils/mb/Unicode/euc_jp_to_utf8.map`, ~4000 entries)
was out of scope for that loop.

That shortcut does not work for `euc_kr.sql`: the test's assertion (`position
= 5`) depends on the *actual* decoded Hangul text, not just successful
structural validation — an `ErrUntranslatableChar` stub would make the whole
statement fail with a wrong SQLSTATE instead of returning `5`. A real
byte↔codepoint table was required.

## Real table, not a hand port: `golang.org/x/text/encoding/korean`

Rather than manually transcribing PG's ~2500-entry
`euc_kr_to_utf8.map`/6392-entry `utf8_to_euc_kr.map` radix tables
(`postgres/src/backend/utils/mb/Unicode/`, generated by
`UCS_to_EUC_KR.pl`), `internal/utils/mb/euc_kr.go` uses
`golang.org/x/text/encoding/korean.EUCKR` — already an indirect dependency of
`go.mod` (used directly elsewhere via `golang.org/x/text/unicode/norm`,
`internal/libpq/auth/saslprep.go`). `korean.EUCKR` implements CP949, a strict
superset of KS X 1001 (plain EUC_KR): every byte pair `pg_euckr_verifychar`
accepts as valid EUC_KR is also a valid CP949 pair mapping to the *identical*
Unicode codepoint, so per-character translation through it is faithful, not
approximate, for the full EUC_KR range PG accepts. Verified against the
oracle's own two test strings (`수학` / `과학, 수학, 기술, 삶`) — decodes
byte-for-byte to the codepoints PG's `euc_kr_to_utf8.map` would produce, and
`POSITION()` returns the oracle's `5`.

Structural validation (`eucKRVerifyChar`) is still a direct port of
`pg_euckr_verifychar` (`postgres/src/common/wchar.c:1188-1213`) — simpler than
EUC_JP's (no SS2/SS3 shift bytes; a high-bit lead byte is always exactly 2
bytes, both constrained to `isEucRangeValid`, shared with `euc_jp.go`) — so a
malformed byte sequence still raises PG's `22021 invalid byte sequence`
before ever reaching the x/text decoder. A structurally-valid but *unmapped*
byte pair (a KS X 1001 gap) is detected by checking whether x/text's decoder
substituted U+FFFD (its silent-replacement behavior for unmapped input, no
Go-level error) and reported as `ErrUntranslatableChar` (PG's `22P05`),
matching PG's own separation between the structural check
(`pg_verify_mbstr`) and the table lookup (`LocalToUtf`) in the two-layer
`pg_do_encoding_conversion` pipeline.

## Wiring

- `internal/utils/mb/wchar.go`: added `PG_EUC_KR = 3` (matches
  `postgres/src/include/mb/pg_wchar.h`'s `pg_enc` enum ordering and
  `internal/catalog/encoding.go`'s `pgEncNames[3]`).
- `internal/utils/mb/euc_kr.go` (new): `eucKRVerifyChar`, `euc_kr_to_utf8`,
  `utf8_to_euc_kr`; registers proc OIDs 4364/4365 in `BuiltinConversions`/
  `builtinPair` (matching `pg_proc_seed_data.go`'s real PG regproc OIDs for
  `euc_kr_to_utf8`/`utf8_to_euc_kr`).
- `internal/executor/expr.go`: new `"convert_from"`/`"convert_to"` function-
  call cases. Both go through `mb.DoEncodingConversion` +
  `mb.BuiltinLookup` — the same bootstrap-only conversion-proc resolution
  `maybeConvertCellsForClientEncoding` uses for `client_encoding`
  transcoding (`internal/postmaster/dispatch.go`); a `CREATE
  CONVERSION`-registered proc is not yet consulted by either path (carried
  forward from M0122-0008's scope note, not a new gap).
