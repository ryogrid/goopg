# M0100-0005m — FK violation MESSAGE names the routed leaf partition

Status: implemented (2026-05-15, loop 29)

## Problem

`fk-snapshot.spec` permutations that INSERT into a partitioned parent with
no matching parent-key in the referenced table reported:

```
ERROR:  insert or update on table "fk_parted_pk" violates foreign key constraint "fk_parted_pk_a_fkey"
```

But upstream PostgreSQL reports the **routed leaf partition** as the table
name in the MESSAGE:

```
ERROR:  insert or update on table "fk_parted_pk_2" violates foreign key constraint "fk_parted_pk_a_fkey"
```

The constraint name (`fk_parted_pk_a_fkey`) is correctly inherited from the
partitioned parent — only the table-name slot was wrong.  This was the
sole L21 diff carried as a follow-up from M0100-0005k.

## Root cause

`internal/executor/operators_storage.go::insertOp.Next` called
`checkFKInsert(ctx, o.plan.Table, row)` **before** the partition router ran.
The FK check therefore used the partitioned parent's name in the MESSAGE,
regardless of which leaf the row would actually be written to.

## Fix

Route the row to its leaf partition first, then thread the leaf through the
FK check as a separate `reportTbl` parameter:

1. `assertParentExists(ctx, fkOwnerTbl, reportTbl, fk, vals)` — `fkOwnerTbl`
   provides `ForeignKeys` and feeds `fkConstraintName` (parent's name);
   `reportTbl` provides the MESSAGE's table name (leaf when partition-
   routed).  `reportTbl==nil` falls back to `fkOwnerTbl` for the
   non-partitioned path.
2. `checkFKInsert(ctx, fkOwnerTbl, reportTbl, row)` — same split, threaded
   through to `assertParentExists`.
3. `insertOp.Next` computes `routedPart` once via `routeToPartition` and
   passes it as `reportTbl`.  Partition routing is hoisted above the FK
   check so the leaf is known by the time the FK is evaluated.  The
   downstream partition-write block reuses the same `routedPart` (no
   double-routing).

`fullTableFKCheck` (used by deferred-FK checks at COMMIT time) passes the
same table for both arguments — partition routing already happened at
INSERT time, so the stored child name is whatever the executor saw then.

## Why split the names (not just rename one)

`fk_parted_pk_a_fkey` is the parent's autogenerated constraint name —
inherited by every leaf, never reassembled per-leaf.  If the synthesised
name were derived from the leaf, we would report
`fk_parted_pk_2_a_fkey` (wrong: upstream PG reports the parent's name).
`fkOwnerTbl` is therefore the parent (`o.plan.Table`); `reportTbl` is the
leaf — they are intentionally different in the partition-routed case.
