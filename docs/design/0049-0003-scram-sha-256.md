# SCRAM-SHA-256 Authentication — M0049-0003

| field      | value                         |
|------------|-------------------------------|
| status     | accepted                      |
| date       | 2026-05-05                    |
| supersedes | —                             |

## 1. Problem

goopg supported `trust` and MD5 auth. SCRAM-SHA-256 is the default since
PostgreSQL 14 and is required by psql/pgx/JDBC when servers enforce it.
The cryptographic core (RFC 5802) was already implemented; the missing piece
was a way to load user credentials into the server on startup.

## 2. Design

### 2.1 Existing infrastructure (already present)

| Component | Location |
|---|---|
| SCRAM-SHA-256 crypto (PBKDF2, HMAC, key derivation, proof verification) | `internal/auth/scram.go` |
| SASL wire exchange (`AuthenticationSASL` → `SASLContinue` → `SASLFinal`) | `internal/auth/exchange.go:runSCRAM` |
| `SCRAMServer` state machine | `internal/auth/scram.go:NewSCRAMServer` |
| `NewSCRAMCredential(password)` → `Credential{Type: PasswordSCRAMSHA256}` | `internal/auth/scram.go` |
| pg_hba parser: `scram-sha-256` auth-method | `internal/auth/parser.go` |
| Protocol message writers: `WriteAuthenticationSASL/Continue/Final` | `internal/protocol/messages.go` |

### 2.2 `pg_auth` credential file (`internal/auth/userstore.go`)

New function `LoadUsersFile(path string) (*MapUserStore, error)` reads a
file of `username:secret` lines:

```
# pg_auth — one entry per line
postgres:SCRAM-SHA-256$4096:<salt-b64>$<StoredKey-b64>:<ServerKey-b64>
alice:my-plaintext-password
bob:md5<32 hex chars>
```

- Lines beginning with `#` are comments.
- Secret type is inferred from the prefix: `SCRAM-SHA-256$` → SCRAM verifier;
  `md5` + 32 hex chars → MD5; anything else → plaintext.

### 2.3 Auto-loading in `goopg start` (`cmd/goopg/main.go`)

At startup, if `<datadir>/pg_auth` exists, it is loaded automatically:

```go
pgAuthPath := filepath.Join(*dataDir, "pg_auth")
if _, statErr := os.Stat(pgAuthPath); statErr == nil {
    store, err := auth.LoadUsersFile(pgAuthPath)
    cfg.UserStore = store
}
```

No new flag is needed — the file is discovered by convention, matching
how `pg_hba.conf` is auto-discovered from the data directory.

### 2.4 `cluster.WritePGAuth` (`internal/testutil/cluster/cluster.go`)

Writes `<datadir>/pg_auth` for test clusters:

```go
func (c *Cluster) WritePGAuth(entries map[string]string) error
```

Called before `c.Start()` so the server picks up the credential file.

## 3. Correctness

- `LoadUsersFile` validates SCRAM verifiers via `ParseSCRAMSecret` before
  inserting them; malformed verifiers return an error at startup.
- MD5 credentials are validated via `ParseMD5Stored`.
- The SCRAM exchange's "doomed mode" (unknown user) prevents user enumeration:
  the server proceeds as if a random secret existed.

### 3.1 SASLprep normalization (Follow-up, 2026-07-08, M0122-0008)

Passwords were previously hashed/verified as raw bytes, diverging from
upstream whenever a password contains non-ASCII characters: `pg_saslprep`
(`postgres/src/common/saslprep.c`) canonicalizes passwords per
[RFC 4013] before they ever reach the PBKDF2 key derivation
(`pg_be_scram_build_secret`/`scram_verify_plain_password`,
`postgres/src/backend/libpq/auth-scram.c`).

`internal/auth/saslprep.go` is a straight port of `pg_saslprep`:

- `saslprep_tables.go` holds the six Unicode range tables (non-ASCII space,
  "commonly mapped to nothing", prohibited output, unassigned codepoints,
  RandALCat, LCat), extracted **mechanically** from
  `postgres/src/common/saslprep.c` by a one-off Python script (not
  hand-transcribed) to guarantee byte-identical table data.
- `pgSASLPrep` replicates the algorithm exactly, including one quirk that is
  in upstream's actual code (not just its comment): the "prohibited output"
  and bidi checks run against the **mapped-but-not-yet-NFKC-normalized**
  codepoints, not the final normalized output. NFKC normalization itself
  uses `golang.org/x/text/unicode/norm.NFKC` (chosen over
  `golang.org/x/text/secure/precis.OpaqueString`, which uses NFC per
  RFC 8265 — a different, *not* upstream-compatible normalization form).
- `saslPrepOrOriginal` applies upstream's own graceful-degradation rule:
  invalid UTF-8 or prohibited output falls back to the original password
  unchanged, rather than erroring — matching both call sites in
  `auth-scram.c` (`if (rc == SASLPREP_SUCCESS) password = prep_password;`).
- Wired into `NewSCRAMSecretWithIterations` (mirrors
  `pg_be_scram_build_secret`, used by `CREATE`/`ALTER ROLE ... PASSWORD`)
  and `SCRAMSecret.VerifySCRAMSecretFromPassword` (mirrors
  `scram_verify_plain_password`, used by the `password` auth method against
  a stored SCRAM secret).
- The live SCRAM **exchange** itself (`SCRAMServer.Step`) needs no change:
  the server never re-derives a secret from a plaintext password during a
  real SCRAM handshake, it only checks the client's HMAC proof against the
  already-SASLprepped stored `StoredKey`/`ServerKey` — correctness there
  depends on the connecting client's own SASLprep (e.g. libpq's
  `fe-auth-scram.c`) agreeing with ours, which is exactly what
  `TestE2E_SASLPrepMatchesRealLibpqClient` proves.

**Still open** (unrelated follow-up, larger scope): TLS channel binding
(`SCRAM-SHA-256-PLUS`, `p=tls-server-end-point`) is fully unimplemented —
goopg always advertises plain `SCRAM-SHA-256` and sends `n,,` — needs
`tls-server-end-point` channel-binding data plumbed from the TLS layer.

## 3b. Channel-binding-flag downgrade protection (2026-07-12, M0122-0008)

Even without `SCRAM-SHA-256-PLUS`, RFC 5802 requires the server to detect
tampering of the negotiated `gs2-cbind-flag` when *no* binding is in use.
The client repeats its original flag inside the `c=` attribute of
client-final-message: base64(`"n,,"`) = `biws` for flag `n`,
base64(`"y,,"`) = `eSws` for flag `y`. Upstream's
`read_client_final_message` (`postgres/src/backend/libpq/auth-scram.c:211`)
rejects a `c=` value whose flag differs from the one recorded in
client-first:

```c
if (!(strcmp(channel_binding, "biws") == 0 && state->cbind_flag == 'n') &&
    !(strcmp(channel_binding, "eSws") == 0 && state->cbind_flag == 'y'))
    ereport(ERROR, ... "unexpected SCRAM channel-binding attribute ...");
```

goopg previously accepted *either* spelling regardless of the original
flag (`validNoBindingChannelAttr` matched `"n,," || "y,,"`), so a MITM
could flip the flag between the two messages undetected. The fix records
the flag byte in a new `SCRAMServer.cbindFlag` field during
`handleClientFirst` and threads it into
`validNoBindingChannelAttr(c, cbindFlag)`, which now returns true only for
the matching pair. Because the `c=` check runs *before* the proof check in
`handleClientFinal`, a tampered flag fails with the channel-binding error
rather than leaking to `ErrInvalidPassword`. Regression tests:
`TestSCRAMExchangeRejectsChannelBindingFlagMismatch` (client sends `n`,
replays `y,,` → rejected before proof) and `TestSCRAMExchangeAcceptsYFlag`
(the legitimate `y`-flag path still completes a full handshake).
