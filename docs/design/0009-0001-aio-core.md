# 0009-0001 — AIO Core (M0009)

Status: accepted (first slice)

## Goal

Lay the foundational submit / wait / complete contract that
every later AIO caller (read stream, checkpointer, WAL writer)
will use. Get the core API and the two universally-available
methods (`sync` and `worker`) in place behind upstream-aligned
GUCs, so subsequent slices can layer on without re-litigating
the surface.

## Substrate

`internal/aio/` ships:

```go
type Direction int          // DirRead, DirWrite
type File interface { io.ReaderAt; io.WriterAt }
type Op struct { File; Buffer []byte; Offset int64; Direction; Callback func(Result) }
type Result struct { N int; Err error }
type Handle struct { ... }
func (h *Handle) Wait() Result

type Method interface {
    Submit(*Op) *Handle
    Close() error
    Name() string
}

type Engine struct { ... }
type EngineConfig struct { Method string; Workers int; MaxConcurrency int }
func NewEngine(EngineConfig) (*Engine, error)
func (e *Engine) Submit(Op) *Handle
func (e *Engine) Close() error
func (e *Engine) Stats() Stats
```

### Methods delivered

- **`sync` (`MethodSync`).** Every Submit performs the underlying
  syscall on the calling goroutine and returns a Handle whose
  Wait is already complete. Useful as the safe default on every
  platform and as a fast-path for tests / micro-benchmarks that
  want to opt out of the worker pool. Backpressure: a buffered
  semaphore caps in-flight Submits when `MaxConcurrency > 0`.

- **`worker` (`MethodWorker`).** A fixed-size goroutine pool
  drains a bounded submission channel; each worker performs
  `pread` / `pwrite` on the caller's behalf. The channel
  doubles as the work queue and the concurrency bound (channel
  capacity == max in-flight). One allocation per Submit instead
  of two. Submission blocks once the channel is full, providing
  the back-pressure the upstream `worker` method relies on.
  Default depth: `4 × workers` when `MaxConcurrency == 0`.

### Methods deferred

- **`io_uring` (`MethodIOUring`).** Linux-only, gated on a
  runtime probe of `io_uring_setup(2)` availability. Selecting
  it in `NewEngine` returns `ErrUnsupportedMethod` until the
  follow-up slice lands. Operators that need the worker fallback
  in the meantime can set `io_method = worker`.

### Counters

The `Engine` carries process-wide atomic counters:

- `Submitted` / `Completed` — every Submit / completion bumps
  the corresponding counter.
- `Errored` — completed Ops whose `Result.Err != nil` and is
  not `io.EOF`. EOF is an expected read outcome upstream, not
  a failure.
- `InFlight` — incremented at Submit, decremented at completion.

`Engine.Stats()` returns a coherent snapshot. The follow-up
observability slice (`0009-0004`) will surface these via
`pg_aios` plus the existing wait-event surface.

## GUCs

`internal/config/defaults.go` registers the upstream-aligned set:

| GUC | Default | Range | Semantics |
|---|---|---|---|
| `io_method` | `worker` | `sync` / `worker` / `io_uring` | Selects the active method. `io_uring` returns `ErrUnsupportedMethod` for now. |
| `io_workers` | `3` | `1..1024` | Goroutine count for `worker`. Mirrors upstream's default. |
| `io_max_concurrency` | `0` | `0..1024` | Global in-flight cap. `0` lets the method pick its default (`4 × workers` for `worker`; uncapped for `sync`). |

All three are `ContextPostmaster` — changes require a server
restart, mirroring upstream. They are registered but not yet
*consumed*: no caller (buffer manager, checkpointer, WAL writer)
plumbs through the engine in this slice. That wiring is the
follow-up.

## Why a `File` interface, not `*os.File`

Two reasons:

1. **Testability.** The package's tests use an in-memory
   `memFile{ buf []byte }` with `sync.Mutex`-guarded
   `ReadAt` / `WriteAt`. Nothing in the engine cares whether the
   underlying handle is an OS file, an in-memory buffer, or a
   block device — only that pread / pwrite semantics hold.
2. **Future direct-I/O / O_DIRECT path.** When M0010's WAL
   direct-I/O lands, the WAL writer can hand the engine a
   `File` whose `WriteAt` enforces alignment. The engine
   doesn't need to learn anything new.

## Error model

- `Result.Err` is whatever `ReadAt` / `WriteAt` returned.
- `io.EOF` is bubbled as-is on short reads (matches `ReaderAt`'s
  documented contract).
- An engine-closed Submit returns a Handle whose Wait yields
  `errEngineClosed`. Callers that race shutdown don't deadlock.
- `NewEngine` rejects unknown methods (and `io_uring` until
  it's implemented) with `ErrUnsupportedMethod`.

Logging never fails an I/O. The engine has no `*slog.Logger`
seam in this slice — call sites already log; the engine is a
mechanism, not a policy surface. The follow-up observability
slice adds structured event emission.

## Verification

`internal/aio/aio_test.go` ships eight tests:

- **TestEngineSyncReadWriteRoundTrip** — the foundational
  contract: write Submit then read Submit at the same offset
  round-trips bytes through the sync method; counters reflect
  both Ops.
- **TestEngineSyncCallback** — the optional Callback fires
  after I/O completes and sees the same Result Wait returns.
- **TestEngineSyncWaitIdempotent** — calling Wait twice on the
  same handle returns the same Result without blocking.
- **TestEngineWorkerParallelExecution** — 100 concurrent writes
  through the worker method against the same memFile commit
  cleanly; the in-flight counter never exceeds the cap.
- **TestEngineWorkerSubmitAfterCloseSurfacesError** — a Submit
  that races against Close returns a Handle whose Wait yields
  the engine-closed error rather than deadlocking.
- **TestNewEngineRejectsIOUring** — `MethodIOUring` returns
  `ErrUnsupportedMethod`.
- **TestNewEngineRejectsUnknown** — an arbitrary method name
  returns `ErrUnsupportedMethod` with the offending value in
  the message.
- **TestEngineSyncReadEOF** — a read past EOF surfaces `io.EOF`
  in `Result.Err` but does NOT count as an error in the
  Errored counter (matches upstream's semantics).

## What this slice doesn't deliver

- `io_uring` method.
- Read-stream API on top of the core (next slice,
  `0009-0002-read-stream.md`).
- Caller integrations: sequential / bitmap heap scan,
  checkpointer dirty-page writeback, WAL writer
  (`0009-0003-aio-checkpointer-and-wal.md`).
- `pg_aios` virtual catalog view, AIO counters in stats
  surfaces, AIO wait events, the startup log line
  (`0009-0004-aio-observability.md`).
- Per-backend in-flight cap (the engine has only the global
  cap; per-backend limits land alongside the read-stream
  integration so one query plan can't monopolise the pool).
- O_DIRECT / direct-IO. Out of scope for M0009 entirely.
