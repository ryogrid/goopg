## 1. Problem

A heap page is 8 KiB. After headers and line-pointer bookkeeping, a single
tuple can occupy at most ~8 168 bytes. A table with a `text` column carrying
1 MiB values cannot be stored at all in this model.

PostgreSQL solves this via TOAST (The Oversized-Attribute Storage Technique):
values larger than a threshold are sliced into fixed-size chunks and stored
in a companion "TOAST table". The main heap stores a compact 12-byte pointer;
the original value is reassembled on demand.

## 2. Design

### 2.1 TOAST threshold

`ToastThreshold = 2000` bytes. Values smaller than this are stored inline.
`ToastMaxChunkSize = 1996` bytes per chunk.

### 2.2 KindToastPointer datum (`internal/executor/datum.go`)

A new `KindToastPointer DatumKind` constant is added. Its 12-byte payload
(stored in `Datum.Bytes`) encodes:

```
toast_oid(4) | total_len(4) | num_chunks(4)
```

`toast_oid` is a process-unique OID assigned from a global atomic counter
(`toastOIDCounter`). It identifies all chunks belonging to one TOAST value.

### 2.3 Codec encoding (`internal/executor/codec.go`)

`EncodeRow` and `DecodeRowInto` use a 3-state null-flag byte:
- `0` — non-null inline value
- `1` — NULL
- `2` — **TOAST pointer** (12 bytes follow, no further value bytes)

No changes to the 0/1 path. `KindToastPointer` datums use the `2` path.

### 2.4 TOAST storage (`internal/executor/toast.go`)

**`ToastRelFor(mainRel)`** derives the TOAST relation from the main heap:
`RelOid = mainRel.RelOid + 100_000_000`. Same `DBOid` and `Fork = MainFork`.
The TOAST file is created on demand (the storage manager's `MkdirAll` +
`O_CREATE` flags handle this transparently).

**`ToastLargeColumnsIfNeeded(ctx, rel, cols, row)`** is called from
`writeHeapRowReturning` before `EncodeRow`. For each toastable column
(`text`, `varchar`, `bytea`, etc.) with a value larger than `ToastThreshold`,
it calls `toastStore` and replaces the datum with `KindToastPointer`.

**`toastStore(ctx, toastRel, data)`** slices `data` into `ToastMaxChunkSize`
chunks, writes each as a heap tuple via `writeHeapTupleToRel`, and returns
the 12-byte pointer.

**Chunk row schema** (encoded with `EncodeRow` using `toastCols`):
- `chunk_id int4` — the `toast_oid`
- `chunk_seq int4` — sequence number (0-based)
- `chunk_data bytea` — up to `ToastMaxChunkSize` bytes

**`DetoastValue(ctx, toastRel, pointer)`** scans every page of the TOAST
relation, collects all chunks with matching `toast_oid`, and concatenates
them in `chunk_seq` order.

Note: `decodeValue`'s default (varlen) case returns `KindString` rather than
`KindBytes` — `DetoastValue` accepts both `KindString` and `KindBytes` when
reassembling chunks.

**`DetoastRow(ctx, mainRel, cols, row)`** resolves all `KindToastPointer`
datums in a row, returning the original data as `KindString` (text types) or
`KindBytes` (bytea).

### 2.5 Insert path (`internal/executor/operators_storage.go`)

`writeHeapRowReturning` calls `ToastLargeColumnsIfNeeded` before `EncodeRow`.
If any column exceeds the threshold, its datum is replaced with a pointer;
the main heap tuple stays within one page.

### 2.6 Scan paths

`seqScanOp.Next()` calls `DetoastRow` when `needsDetoast(row)` is true
(after `DecodeRow`).

`indexScanOp.Open()` `scanFn` calls `DetoastRow` after the heap fetch.

## 3. Limitations (v0)

- No compression (pglz deferred).
- Process-unique OIDs only — OID counter resets on restart; stale TOAST
  tables from prior sessions are abandoned (harmless since the main heap is
  dropped simultaneously).
- No VACUUM integration for TOAST tables (dead TOAST chunks accumulate until
  the table is dropped).
- `DetoastValue` does a full sequential scan of the TOAST table — O(N pages)
  for every detoast. An index on `(chunk_id, chunk_seq)` is deferred.
