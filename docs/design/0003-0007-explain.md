## Problem

The M0003 planner now picks between hash-join and nested-loop
based on predicate shape (see
[0003-0002-join-executors.md](0003-0002-join-executors.md)),
but there's no surface to verify the choice without forcing
the inner query through psql and reading the row count
patterns. EXPLAIN closes that gap.

## Upstream reference

- `postgres/src/backend/commands/explain.c` —
  `ExplainOnePlan` and the per-node `ExplainNode` recursion.
- `postgres/src/backend/parser/gram.y` — `ExplainStmt` /
  `explain_option_list`.

## Decisions

### v0 scope: text format, no options

`EXPLAIN <stmt>` only — no option list, no `ANALYZE`, no
`VERBOSE`, no `FORMAT JSON`. Adding parser support for the
optional `( option [, ...] )` clause is one of the deferred
items below.

The output is a single-column `QUERY PLAN` text result. Each
row is one plan node rendered as `<indent>->  <label>`,
matching upstream's text format closely enough that `psql`
formats it identically. The root row has no leading `->`.

Example (a TPC-H-shaped join plan):

```
          QUERY PLAN
------------------------------
 Projection
   ->  Hash Join (INNER)
     ->  Seq Scan on customer
     ->  Seq Scan on orders
```

### Plan-tree rendering: pre-order walk, indent per depth

`explainOp` runs the inner plan through a pre-order walk
(`walkPlan`) keyed by depth. Every plan-node case in
`describePlan` returns one short label; node-specific details
are surfaced as parenthesised hints:

| Node type             | Label                                  |
| --------------------- | -------------------------------------- |
| Project / Filter / Sort / Limit | bare name                    |
| Values                | `Values (N rows)`                      |
| Join (NestedLoop)     | `Nested Loop (INNER \| LEFT \| …)`     |
| Join (Hash)           | `Hash Join (INNER \| LEFT \| …)`       |
| Aggregate (no GROUP)  | `Aggregate (N aggregates)`             |
| Aggregate (GROUP BY)  | `GroupAggregate (K keys, N aggregates)`|
| SeqScan               | `Seq Scan on <relation>`               |
| IndexScan             | `Index Scan using <index> on <table>`  |
| Insert / Update / Delete | `<verb> on <relation>`              |
| Transaction           | `Transaction (verb)`                   |
| Checkpoint            | `Checkpoint`                           |

`planChildren` is the recursion oracle. It exposes only the
public Node fields each node type carries — no introspection
into Update/Delete sub-trees yet (those resolve their scan
children at executor time, not planning time, so EXPLAIN
shows the bare DML node for now).

### Planner integration: thin Explain node

`planner.Explain{Child Node}` is the simplest possible
wrapper. The planner builds the inner plan eagerly inside
`Plan(stmt)` so any planning errors surface at EXPLAIN time
(matches upstream's behaviour). The Explain node itself
declares a single-column `QUERY PLAN` schema so RowDescription
is correct on the wire.

### Wire-protocol shape: SELECT-shaped result, EXPLAIN command tag

The dispatch layer reads `*planner.Explain` as a read-shaped
plan but overrides the CommandComplete tag to the bare
`EXPLAIN` (matching upstream's libpq `PQcmdStatus`). The
RowDescription comes from the Explain node's Output().

## Verification

End-to-end via `goopg start -D <dir>` with upstream psql 18.3:

```
EXPLAIN SELECT c_name FROM customer JOIN orders ON c_custkey = o_custkey;
-- shows "Hash Join (INNER)" with two Seq Scan children

EXPLAIN SELECT c_name FROM customer JOIN orders ON c_custkey < o_custkey;
-- shows "Nested Loop (INNER)" — predicate doesn't decompose

EXPLAIN SELECT count(*) FROM customer;
-- shows "Aggregate (1 aggregates) -> Seq Scan on customer"

EXPLAIN SELECT c_name FROM customer WHERE c_custkey = 1 ORDER BY c_name LIMIT 3;
-- shows the Project / Limit / Sort / Filter / Seq Scan stack
```

`TestParseExplainWrapsInner` pins that EXPLAIN parses as a
statement wrapping the inner-statement AST verbatim.

## Out of scope (deferred to subsequent loops)

- `EXPLAIN ANALYZE` (executes + collects per-node row counts
  / timing). Needs an executor instrumentation pass that
  hooks Open/Next/Close to record per-operator metrics.
- `EXPLAIN ( FORMAT JSON | YAML | XML )`. The text-format
  rendering is the v0 baseline; structured formats are a
  small follow-up that reuses the same describe table.
- `EXPLAIN ( VERBOSE )` — surfaces output columns and
  rangetable aliases. Useful when type unification questions
  arise; deferred.
- `EXPLAIN ( COSTS )` — needs cardinality estimates from
  the statistics milestone.
- Sub-plan rendering inside Update / Delete (the source-of-
  modification scan tree). v0's planner produces those at
  build time inside the executor, so EXPLAIN doesn't see
  them yet.
