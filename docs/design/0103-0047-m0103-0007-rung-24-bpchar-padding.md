# M0103-0007 rung 24 — `filler char(N)` bpchar padding through pgoutput (PG → goopg)

Status: accepted (2026-05-14)

## Goal

Pin that pgoutput correctly replicates fixed-length blank-padded
`char(N)` / `bpchar(N)` column values from a PG publisher to a goopg
subscriber, end-to-end through the same apply path rungs 1–23 already
cover. Rungs 1–23 only exercised variable-length text (`text`, `varchar`)
column types — `char(N)` is a separate codec path on both ends:

- Publisher: PG's pgoutput emits bpchar values as N-byte text padded with
  trailing spaces (the standard bpchar text-output function).
- Apply worker: `parsePgoutputText` falls through to the variable-length
  text fallback (`NewStringDatum(s)`) for bpchar — there is no bpchar
  branch, the padded wire text goes in as-is.
- Storage encoder: `internal/executor/codec.go::encodeAttr`'s bpchar
  branch right-strips trailing spaces before writing the heap tuple, so
  storage stays compact and `compareDatum` keeps PG's
  padding-insensitive bpchar equality semantics.
- Dispatch DataRow path: re-pads to declared width N on the wire so
  `SELECT filler FROM t` over goopg matches PG's bpchar output shape.

Rung 24 fixes the bpchar tpcb-like `filler char(N)` columns that rung 21
dropped from its scaled-down pgbench schema (see the comment at
`internal/testport/pgoutput_interop_test.go:1842` — "filler columns
dropped … `char(N)` padding through pgoutput is out of rung 21's
UPDATE-apply scope"). Pinning the bpchar wire roundtrip independently
closes that hole.

## Non-goals

- pgbench-driven workload against the full standard
  `pgbench_accounts(... filler char(84))` schema. Out of scope; rungs 20
  / 21 already pinned the pgbench-driver path against schemas without
  the filler column, and this rung's goal is wire correctness of the
  bpchar type, not workload coverage.
- `varchar(N)` length-truncation roundtrips. Variable-length text was
  already exercised in rungs 1, 4, and others; bpchar is the missing
  type.
- Binary-format pgoutput. pgoutput's column-output format is text in
  every rung so far; binary format requires `binary` SUBSCRIPTION option
  + per-type send/recv functions on both sides, separate scope.
- Domain-over-bpchar, citext, or other text-family types. Out of scope.
- `sync_remote_apply` mode, `proto_version=2` streaming, kill mid-flight
  bpchar workloads. Separate rungs.

## Design

The rung is a pure wire-correctness test. No goopg code change is
required: the apply-worker fallback already routes bpchar text through
`NewStringDatum`, and the storage encoder already strips, and the
dispatch path already re-pads. The rung pins that all three pieces
compose correctly end-to-end.

### Fixture shape

```
CREATE TABLE public.bpchar_log (
    id     int PRIMARY KEY,
    code   char(1)    NOT NULL,   -- bare char defaults to char(1)
    filler char(20)
)
```

`code` exercises the bare-`char` path that PG defaults to char(1); the
`NOT NULL` guards against a silent regression that landed everything as
NULL. `filler` is nullable so the rung also pins the bpchar-NULL path
through pgoutput.

### Workload

Four INSERTs + one UPDATE on the PG publisher, then wait for replication
to drain. Each INSERT exercises a different bpchar shape:

| id | code | filler                | shape exercised                       |
|----|------|-----------------------|---------------------------------------|
| 1  | 'A'  | 'ab'                  | short value, will be padded to 20     |
| 2  | 'B'  | 'X'                   | minimum-length value                  |
| 3  | 'C'  | 'twenty char filler'  | 18 chars (just under N)               |
| 4  | 'D'  | NULL                  | NULL bpchar                           |

Then `UPDATE public.bpchar_log SET filler = 'new' WHERE id = 1` to
exercise the UPDATE path with a bpchar new value.

### Assertions

The subscriber-side checks rely on goopg's `length()` and equality
semantics, both of which operate on the stripped storage form so they
match PG's bpchar semantics (PG's `length(bpchar)` excludes trailing
spaces by definition; bpchar equality is padding-insensitive).

After waiting for `count(*) = 4`:

1. `count(*) = 4` — all four INSERTs landed.
2. `count(filler) = 3` — NULL bpchar at id=4 made it through pgoutput.
3. `length(filler) = 3` where id=1 — UPDATE replaced 'ab' with 'new'.
4. `length(filler) = 1` where id=2 — minimum-length value preserved.
5. `length(filler) = 18` where id=3 — under-N value preserved.
6. `filler IS NULL` where id=4 — NULL did not become empty string.
7. `code = 'A'` where id=1 — char(1) NOT NULL value made it through.

`length()` over the stripped form catches:
- The codec failing to strip trailing pad bytes (would observe
  `length = 20` instead of the value length).
- pgoutput sending a different bpchar shape than expected (e.g. binary
  bytes, length-prefixed framing).
- The apply-worker storing the wire bytes literally instead of decoding
  via `parsePgoutputText` (would observe an extra status byte or NULL
  marker stored as text).

The UPDATE check pins that REPLICA IDENTITY DEFAULT (PK on `id`) lets
the apply worker locate the existing row and rewrite the bpchar column
correctly — same path rungs 2 / 21 pin for text/varchar columns.

## Tests

Pinned by `TestPort_PgoutputInteropPGToGoopgBpcharPadding` in
`internal/testport/pgoutput_interop_test.go`. No new helper — the test
uses the existing `pubsubcluster.NewMixed` harness, `psc.WaitForRow`,
and `psc.Subscriber.QueryScalar`. `baseDir` kept short (`pg2g-bpchar`)
for the 108-byte Unix-sockaddr limit.

## Out of scope (deferred within M0103-0007)

- `sync_remote_apply` zero-loss kill subtest.
- `proto_version=2` subxact streaming.
- column-ref-typed `nextval` args.
- Binary-format pgoutput.
