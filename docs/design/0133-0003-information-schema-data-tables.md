# M0133-S3 — `information_schema` data tables + 801 rows

**Status:** accepted — landed 2026-08-13.
**Milestone:** M0133 (`information_schema` on disk), slice S3.
**Supersedes:** S9.4c in `0131-0009-system-view-corpus-widening.md` §"Successor decomposition".

## What landed

The four **ordinary heap tables** `information_schema.sql` creates near its end —
`sql_features` (755 rows), `sql_sizing` (23), `sql_implementation_info` (12),
`sql_parts` (11), 801 rows total — seeded on disk with real data. A hosted PG 18.3
cold-started on a goopg `$PGDATA` now answers `SELECT * FROM
information_schema.sql_features` with all 755 rows (not just a plan), and the
row types / column types resolve by name.

This is the first **bulk heap load at initdb time** goopg has ever done: every
prior on-disk catalog heap (`pg_class`, `pg_attribute`, `pg_type`, `pg_proc`, …)
is a *metadata* table whose rows are generated by a `bootstrapXxxTuples` writer;
these four are *data* tables whose rows upstream `COPY`s from `sql_features.txt`
(`postgres/src/bin/initdb/initdb.c:1981`). The row data is captured verbatim
from a fresh PG 18.3 (the same "measure, don't read a `.dat`" rule S1/S2 used),
committed as four TSV files, and `//go:embed`-ed rather than regenerated.

## Measured object graph

The four tables sit at the end of `information_schema.sql` (lines 1710/1730/1759/
1785), so their OIDs come from the same post-bootstrap counter as S1's domains and
S4's views. Each `CREATE TABLE` consumes **five** OIDs, and every table carries a
TOAST pair because `character_data` is a varlena column:

| name | OID T | reltype T+2 | reltoastrelid T+3 | toast idx T+4 | cols |
|---|---|---|---|---|---|
| `sql_features` | 13456 | 13458 | 13459 | 13460 | 7 |
| `sql_implementation_info` | 13461 | 13463 | 13464 | 13465 | 5 |
| `sql_parts` | 13466 | 13468 | 13469 | 13470 | 5 |
| `sql_sizing` | 13471 | 13473 | 13474 | 13475 | 4 |

For each table the five objects are (measured, not assumed):

1. **`pg_class` table row** — relkind `'r'`, relnamespace 13273, reltype T+2,
   relam 2 (heap), relfilenode T, reltoastrelid T+3, relhasindex **f** (the
   TOAST index does not set the parent's `relhasindex`), relnatts N.
2. **`pg_type` array row** (T+1) — `_<name>`, typtype `'b'`, category `A`,
   typelem T+2, typarray 0, array_in/out/recv/send (750/751/2400/2401),
   typsubscript 6179 (`array_subscript_handler`), typanalyze 3816,
   typalign **`'d'`** (an array aligns to its element — here a composite), -1.
3. **`pg_type` composite row** (T+2) — `<name>`, typtype `'c'`, category `C`,
   typrelid T, typarray T+1, record_in/out/recv/send (2290/2291/2402/2403),
   typalign `'d'`, typstorage `'x'`, -1.
4. **`pg_class` TOAST heap** (T+3) — relkind `'t'`, relnamespace 99,
   relam 2, reltoastrelid 0, relhasindex **t**, relnatts 3.
5. **`pg_class` TOAST index** (T+4) — relkind `'i'`, relnamespace 99, relam 403
   (btree), relnatts 2; `pg_index` row indrelid T+3, indkey `{1,2}`,
   indclass `{oid_ops,int4_ops}`, UNIQUE PRIMARY.

Column types are the three S1 domains — **`character_data`** (13290, varlena,
attlen -1, align `i`, storage `x`, attcollation **950**), **`yes_or_no`** (13300,
same but declared `varchar(3)`), **`cardinal_number`** (13287, int4, attlen 4,
byval, storage `p`, attcollation 0). All 26 user columns are nullable
(`attnotnull` f). goopg follows its existing convention of seeding **user columns
only** — the six negative-attnum system-attribute rows upstream emits are a known
ledgered divergence (see `pg_rewrite_toast_bootstrap.go`).

## Design

### 1. Relation list — `informationSchemaDataTableRels()`

A new list (not `nailedLocalRels`, not `nailedToastRels()`) that carries the four
tables as `nailedRel{RelKind:'r', RelType:T+2, Attrs:…}`. It must NOT ride
`nailedLocalRels`, which would drag the tables into `pg_internal.init`
(`writeRelcacheInitFile`) — upstream never nails `information_schema` relations,
and the init file is reserved for critical catalogs. It must NOT ride
`nailedToastRels()`, whose rels carry `RelType 0` and are excluded from the
`pg_type` bootstrap. It is appended at exactly the five iteration sites that feed
on-disk `pg_class`/`pg_attribute`/`pg_type`/index content, and nowhere else:

- `bootstrapPgClassTuples` (pg_class heap) — the oid index (2662) is TID-derived,
  so it follows automatically.
- `bootstrapPgAttributeTuples` (pg_attribute heap) — the relid-attnum index
  (2656) is TID-derived likewise.
- `bootstrapPgClassRelnameNspIndex` (2663) — the only pg_class index iterated
  explicitly; omitting here leaves the table unresolvable *by name*.
- `pgTypeOIDsUsedByNailedAttrs` — column type OIDs (already covered by S1's
  domain OIDs, but kept exhaustive).
- `pgTypeBootstrapEntryMap`'s RelType loop — the composite rowtypes (T+2).

### 2. Composite + array `pg_type` rows

Eight `pgTypeCanonical` cases (4 composite + 4 array), plus three overlays:

- `pgTypeRelidOverlay[T+2] = T` — a composite's `typrelid` is mandatory; PG's
  `lookup_type_cache` asserts `OidIsValid(typrelid)` for `typtype='c'`.
- `pgTypeNamespaceOverlay` — T+1/T+2 → 13273 (default is 11).
- `pgTypeElemArraySubscriptForOID` — composite `{typelem 0, typarray T+1,
  typsubscript 0}`; array `{typelem T+2, typarray 0, typsubscript 6179}`.

The composite uses record_in/out/recv/send; the array uses the standard
array quad, with typalign `'d'` (not the `'i'` S1 gave `_cardinal_number`, whose
element is int4 — an array aligns to its element).

### 3. TOAST pairs — `nailedToastPairs()`

Four new `toastRelPair{Parent:T, ToastRel:T+3, ToastIdx:T+4, RelName:"pg_toast_<T>"}`
entries. This is *exactly* what M0131-S20.1 built for `pg_rewrite` (2838/2839);
everything downstream — `nailedToastRels()` (pg_class/pg_attribute rows),
`bootstrapToastRelationFiles` (empty heap + metapage-only index), and
`pgClassReltoastrelidFor` — keys off that one list. The empty pair is byte-for-byte
what upstream's own initdb leaves behind, because no `information_schema` datum
exceeds the ~8160 B inline budget (max column is `sub_feature_name` at 120 B), so
no value is ever toasted. Four `pg_index` rows are added alongside 2839's.

### 4. Domain-typed columns — three small fixes

The tables' columns are *domains*, which the `pg_attribute` writer derives attlen/
attbyval/attalign/attstorage from by OID. Three helper gaps surfaced:

- `pgTypeByVal` — 13287 (`cardinal_number`) is by-value (int4 base).
- `pgTypeStorageChar` — 13290/13300 are `'x'` (varlena base), not the `'p'`
  default.
- **attcollation** — `pgAttributeRow` hardcoded `attcollation = 0`, which is fine
  for nailed catalogs (PG loads their descriptors from `pg_internal.init`) but
  wrong for these *non-nailed* tables, whose heap `pg_attribute` is the sole
  source. A `nailedAttr.Collation` field (default 0) carries 950 for the
  `character_data`/`yes_or_no` columns so `ORDER BY`/comparisons on those columns
  use `C` collation, matching upstream.

### 5. The 801 rows — embed + parse + `writeMultiPageHeapRows`

The four TSV captures (one per table, `\N` = NULL, tab-separated, `is_verified_by`
NULL on every `sql_features` row — upstream's COPY omits it) are committed under
`internal/initdb/` and `//go:embed`-ed. `informationSchemaTableRows()` parses them
into `[]executor.Row` and `informationSchemaTableCols()` returns the matching
`catalog.Column` list. The **encoding** deliberately uses base type names —
`text` for `character_data`/`yes_or_no`, `int4` for `cardinal_number` — because a
domain stores its base type's binary representation, and `EncodeRowPG` has no
domain cases. The **pg_attribute** rows carry the domain OIDs (13290/13300/13287);
only the heap writer's `catalog.Column` list is base-typed. The two are decoupled
by construction: `nailedAttr.TypeOID` feeds pg_attribute, `catalog.Column.Type`
feeds the encoder.

`bootstrapInformationSchemaDataTables` calls `writeMultiPageHeapRows` once per
table (relfilenode = table OID), writing `base/{1,5}` (template1 + postgres;
template0 is re-materialised from base/5 by M0131-S15, matching upstream's
`CREATE DATABASE template0 … STRATEGY = file_copy`).

## Findings

**F1 — a table is five OIDs, and the TOAST index does not set `relhasindex`.**
The OID band between tables is 5 (table, array type, composite type, toast heap,
toast index), and the parent's `relhasindex` stays `f` despite owning a toast
index — the toast index is invisible to that flag upstream.

**F2 — `sql_parts` has no `GRANT SELECT`.** `information_schema.sql` grants PUBLIC
SELECT on the other three tables but not `sql_parts`, so its `relacl` is NULL
(owner-only) while the others carry `{postgres=arwdDxtm/postgres,=r/postgres}`.
goopg writes the existing `relacl = "{}"` convention for all four — a divergence
ledgered below; the gate (superuser `SELECT`) is unaffected.

**F3 — the encoding/descriptor split is load-bearing.** If the heap writer's
column list used the domain names, `EncodeRowPG` would reject them; if the
pg_attribute rows used base type names, a hosted PG's `pg_typeof` would report
`text`/`integer` instead of `character_data`/`cardinal_number`. The two lists are
kept separate and a guard asserts they stay aligned.

**F4 — domain-typed expressions are unresolvable on a hosted PG (pre-existing,
ledgered).** `WHERE feature_id = 'B011'` fails `operator is not unique:
information_schema.character_data = unknown` (and `||`/`concat` likewise) where a
real PG 18.3 resolves them to text. The operators (`texteq`), the casts
(varchar→text), and the domain's `typbasetype` are all present on disk — the gap
is inside PG's own `oper()` domain→base reduction against goopg's catalog, not a
missing operator/cast row. Projection + `count(*)` (this slice's gate) are
unaffected; the E2E probe asserts cell content via `LIMIT` on heap order rather
than a WHERE clause. This blocks S4's views (they filter on `character_data`/
`yes_or_no`), so it must be triaged before S4's end-to-end view evaluation.

## Guards

- `TestInformationSchemaTableRowsMatchCapture` — the embedded TSV parses to
  exactly 755/23/12/11 rows, and a spot-checked cell equals the oracle value
  (e.g. `sql_features` row `B011`/`Embedded Ada`/`NO`, `sql_sizing` `MAXIMUM
  IDENTIFIER LENGTH` = 63, `sql_implementation_info` DBMS VERSION =
  `18.03.0000`).
- `TestInformationSchemaDataTableRelsNotInInitFile` — the four table OIDs are in
  neither `nailedSharedRels` nor `nailedLocalRels` (i.e. `writeRelcacheInitFile`
  never sees them), and each carries a non-zero `RelType` + a `reltoastrelid`
  in `nailedToastPairs`.
- E2E `assertInformationSchemaDataTablesReadable` (hosted PG) — `SELECT count(*)`
  returns 755/23/12/11 and `SELECT feature_name FROM sql_features WHERE
  feature_id='B011'` returns `Embedded Ada`.

Gates: `internal/initdb` PASS, `internal/catalog` PASS,
`TestE2E_PGColdStartOnGoopgDataDir` PASS, `go build ./...` + `go vet` clean.
