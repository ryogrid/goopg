# 2026-08-05 — P5.6-g-ii: what crosses a grouping node is uniqueness, not statistics

Instruments:

- `cmd/estimate-audit --label 2026-08-05-p56gii --port 65433 --db tpch
  --timeout 150s` → `2026-08-05-p56gii.txt` (+ `.plans.txt`), against the
  TPC-H goopg cluster (SF=1, HammerDB load, `lineitem` = 5 997 241) started
  under the cgroup cap at `GOGC=100 GOMEMLIMIT=12GiB`.
- `scripts/tpcds-sf05-regression.sh sweep` → `2026-08-05-p56gii-ds05-sweep.txt`,
  plus the plan-shape channel's before/after captures
  (`-plans-before.txt` = `b2d82285`, `-plans-after.txt` = this change).

## 1. The item as filed was the wrong half, and the oracle says so

P5.6-g-ii was filed as "add a `*HashAggregate` arm to `resolveBaseColumn`",
with the measured warning that the arm ALONE reads worse (nd2 = 1 210 559
against nd1 = 1 500 000 → 4.84 M, up from 2.99 M). It reads worse because
**upstream does not have that arm.** `examine_simple_variable` (selfuncs.c),
having walked into a subquery RTE, reaches:

```c
/* The same idea as with DISTINCT clause works for a GROUP-BY too */
if (subquery->groupClause)
{
    if (list_length(subquery->groupClause) == 1 &&
        targetIsInSortList(ste, InvalidOid, subquery->groupClause))
        vardata->isunique = true;
    /* cannot go further */
    return;
}
```

It propagates **uniqueness** and refuses to propagate **statistics**. Grouping
mashes the underlying column's distribution beyond recognition — the MCV list
and the histogram describe the pre-grouping multiset — but it cannot destroy
the fact that one row survives per distinct group value. The consumer is
`get_variable_numdistinct`:

```c
if (vardata->isunique)
    stadistinct = -1.0 * (1.0 - stanullfrac);
```

A negative `stadistinct` is a *fraction of the relation's rows*, and
`stanullfrac` is 0 here because upstream returned before finding a statistics
tuple. The distinct count of a grouped output is therefore exactly its own row
count — which is the truth, not a heuristic.

So the landed shape is: a walk that answers "is this coordinate the sole
grouping / DISTINCT key?" (`resolvesToGroupUniqueColumn`), consumed only in
`columnNDistinctForChild`. `resolveBaseColumn` deliberately still has no
grouping arm, and `columnStatsForChildBase` still answers nil through one — a
test pins that.

## 2. Q18, the joinrel the item was raised for

| | est | actual | ratio |
|---|---|---|---|
| before (`2026-08-05-p56g.txt`) | 2 998 620 | 70 | **42 837×** |
| after (this run) | 1 696 939 | 70 | **24 242×** |
| PG 18.3, same joinrel (`…-p56giii-parity`) | 452 478 | 84 | 5 387× |

`2 998 620` was `5 997 241 × 0.5` exactly — `eqjoinsel_semi`'s punt, taken
because nd2 was unknowable and `defaultNumDistinct` (200) sat far below the
inner's row estimate, so the clamp never rescued it. With the grouping key
unique, nd2 is the inner's own post-HAVING row count and the fraction is
measured. Parity excess against PG drops 8.0× → 4.5×.

**It is still a violation, and the residual is now attributable.** goopg's
`lineitem.l_orderkey` ndistinct is ~1 210 559 against PG's ~339 000; goopg's is
the more accurate (the truth is 1 500 000) and it is what makes goopg's
post-HAVING inner ~3.6× larger than PG's 113 141. Closing the rest means
sizing `HAVING sum(l_quantity) > 313` better than DEFAULT_INEQ_SEL, which is a
different mechanism from this one.

## 3. `reduce_unique_semijoins` is numerically inert here — measured, not assumed

The item's second half was PG's dedup of a `GROUP BY`-unique subquery into a
plain INNER join (`reduce_unique_semijoins`, analyzejoins.c), and PG's Q18 plan
confirms it fires (`Hash Cond: (orders.o_orderkey = lineitem_1.l_orderkey)` is
an INNER hash join, not a Semi Join). **At goopg's join order it changes no
number**: for an inner side unique on the join key, `inner_rows` equals nd2, so
the INNER formula `outer · inner / max(nd1, nd2)` and the SEMI formula
`outer · min(1, nd2/nd1)` agree term for term. What the conversion actually
buys upstream is join-order *freedom* — PG joins `orders ⋈ agg` first (113 141
rows) where goopg joins `orders ⋈ lineitem` first (5 997 241) and semi-joins
that. Deferred with a ledger row rather than implemented blind, because in
goopg a SEMI `*Join`'s `Output()` is left-only and a node-type swap changes the
output width of everything above it.

## 4. The outer-join floor this exposed

`estimateJoin` has never had an outer-join arm: LEFT / RIGHT / FULL took the
INNER product, which is upstream's first line for each of them
(`calc_joinrel_size_estimate`, costsize.c), and stopped before the second —
"the output must be at least as large as the non-nullable input". It stayed
invisible because a LEFT join's key typically resolved to nothing, so the
estimate came from the `defaultEqSelectivity` fallback, which caps at
`max(l, r)` and could not go under the outer's own count by accident.

The grouping arm made those keys resolvable and TPC-DS Q77's
`store LEFT JOIN (… GROUP BY s_store_sk)` immediately estimated **885 rows for
a join whose outer alone is 8 885**. `outerJoinRowFloor` is the missing clamp,
RIGHT included (goopg keeps JOIN_RIGHT where upstream has already commuted it,
so its non-nullable input is the inner).
