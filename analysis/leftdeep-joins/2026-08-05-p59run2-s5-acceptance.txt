# 4. THE HEADLINE — Q5 is wrong on the DEFAULT planner, not on the new one
# ---------------------------------------------------------------------------
# TPC-H Q5 joins six relations and its WHERE contains THREE nation equalities:
#
#     c_nationkey = s_nationkey  AND  s_nationkey = n_nationkey
#     (plus n_regionkey = r_regionkey, r_name = 'ASIA')
#
# {c_nationkey, s_nationkey, n_nationkey} is one equivalence class over three
# relations, so a correct plan must emit TWO clauses from it. The flag-OFF
# plan (explain-off.txt) emits ONE:
#
#     Hash Cond: (customer.c_nationkey = nation.n_nationkey)   <- the only one
#     … supplier joined solely on (lineitem.l_suppkey = supplier.s_suppkey)
#
# `supplier` is therefore never nation-constrained. `l_suppkey = s_suppkey` is
# 1:1, so this does not multiply rows — it ADMITS the ~24 in 25 lineitems
# whose supplier nation differs from the customer's. The revenue sum inflates
# by ~24x. The flag-ON plan emits both, as a two-key hash condition:
#
#     Hash Cond: ((orders.o_custkey = customer.c_custkey)
#             AND (supplier.s_nationkey = customer.c_nationkey))
#
# Measured (`n_name | revenue`, top row):
#
#     PostgreSQL 18.3, :65432 TPC-H SF1     INDONESIA   55,888,676.02
#     goopg GOOPG_PGSHAPED_DP=0 (DEFAULT)   INDIA    1,341,836,898.53   ~24x
#     goopg GOOPG_PGSHAPED_DP=1             INDIA       57,272,646.95
#
# (PG's cluster is a separate SF1 load, so per-nation values are not expected
# to be byte-equal to goopg's HammerDB load — the MAGNITUDE is the evidence,
# and 1.34e9 vs ~5e7 is not a load difference.)
#
# Attribution probe on the SAME goopg data, flag-OFF, three spellings of the
# equivalence (`/tmp/q5ec.sh`, reproduced in §7):
#
#     A  c_nationkey = s_nationkey AND s_nationkey = n_nationkey   1,341,836,898.53
#     B  s_nationkey = c_nationkey AND c_nationkey = n_nationkey   1,341,836,898.53
#     C  all THREE equalities spelled out redundantly              1,341,836,898.53
#
# All identical. The legacy path does not lose the clause because of how the
# user wrote it, and re-stating the dropped equality **explicitly** does not
# bring it back: the equivalence class is formed and then under-emitted, so a
# redundant conjunct is absorbed rather than applied. That rules out "the user
# must spell out the transitive closure" and rules out written-order
# sensitivity; it is a defect in legacy EC clause generation for a class
# spanning three relations.
#
# What this does to the bar: **clause 1 is specified as value equality against
# the flag-OFF arm, and on Q5 the flag-OFF arm is not an oracle.** The
# comparison is still the right instrument — it is what found this — but its
# verdict is directional, not absolute. Amended in 09 §3.4: a non-MATCH cell
# is adjudicated against PostgreSQL, not scored against flag-OFF. Q5's cell is
# now a flag-ON *win* recorded as a bar failure, and it stays a bar failure
# only in the bookkeeping sense until the baseline is fixed.
#
# Filed as **M0119-0011** (a default-path correctness bug, independent of
# M0127 and of the flag) — see §6.
