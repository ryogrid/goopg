#
# ### Where the est=1 comes from — a two-table reproducer
#
# Q12 joins exactly two relations, so there is no search-order confound. Same
# HEAD, same stats, same session; only the flag differs:
#
#   flag OFF:  Hash Join (INNER, build=left)   rows=21154
#                -> Seq Scan on orders          rows=1500000
#                -> Seq Scan on lineitem        rows=21154   Filter: (l_shipmode …)
#
#   flag ON:   Merge Join (INNER)               rows=1
#                Merge Cond: (orders.o_orderkey = lineitem.l_orderkey)
#                -> Index Scan using orders_pk on orders   rows=1
#                     (NO index condition — the o_orderdate/l_* predicates are
#                      not here; this is a full ordered scan of `orders`)
#                -> Seq Scan on lineitem        rows=21154   Filter: (l_shipmode …)
#
# The join is not mis-sized by a join-selectivity error: its OUTER INPUT is
# sized at ONE ROW. An unparameterized index scan — the path the PG-shaped
# search adds for its sortedness, so that a Merge Join becomes available — is
# carrying the row estimate of a parameterized single-row lookup. Every joinrel
# above it then inherits `rows=1` (Q12 has one join level; Q7 and Q9 show the
# same 1 propagating up three and four levels), the cost model can no longer
# rank anything, and the search commits to merge-join spines over full tables.
# Q10's flag-ON plan shows the identical signature: `Index Scan using orders_pk
# on orders  rows=1  Filter: (o_orderdate >= …)`, feeding a Merge Join at
# rows=1 and a Hash Join at rows=1 above it, against 114 106 actual.
#
# The flag-OFF arm also prints `rows=1` on its index scans, but there all 11 of
# them are inner sides of nested loops — genuine one-row lookups — so the
# rendering is correct in that arm and the defect does not surface. The
# discriminator is an index scan used as a full ordered scan, which only the
# PG-shaped search produces.
#
# Not attributed further here: whether the 1 is created when the index path is
# BUILT (a sizing path that assumes an index qual), or whether it is a correct
# path size mis-consumed by `makeJoinRel`/`sizeJoinRel`
# (internal/planner/joinsearchlevel.go:324-330 already clamps `rows < 1` to 1,
# which would MASK a zero as a one). Bisecting that is M0127-P5.9-h's first
# action, and it now has a two-table reproducer instead of a 6-relation one.
#
