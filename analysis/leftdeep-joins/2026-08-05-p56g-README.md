## 1. Result: the change is a measured no-op on TPC-H

Violations **2 → 2**, and both are bit-identical to the P5.6-f-ii baseline:

| query | joinrel | p56fii | p56g |
|---|---|---|---|
| Q18 | final `Hash Join (SEMI)` | est=2 998 620 (42 837× over) | est=2 998 620 (42 837× over) |
| Q21 | final `Hash Join (ANTI)` | est=1 (4 003× under) | est=1 (4 003× under) |

Every other joinrel moved by under 5 %, in both directions, on INNER joins this
change does not touch — that is ANALYZE's sampling noise between two runs, not
the change. It sets the audit's noise floor: **a SEMI/ANTI delta under ~5 % is
not evidence.**

## 2. The mechanism works; TPC-H just cannot exercise it

A measured no-op is indistinguishable from a broken wire unless you separate
them, so both halves were probed on a throwaway cluster (port 5533) with the
SAME binary — the only variable is the input.

**The MCV arm.** One semi-join, two inners with identical `nd2 = 10` and
identical outer (`nd1 = 5 001`, 50 % of the rows on a single key). The only
difference is whether ANALYZE kept an MCV list for the inner:

| inner | MCV list | estimate | actual |
|---|---|---|---|
| 10 values × 2 rows each (uniform) | none — upstream discards a list whose values are not more common than average | **20** | 5 010 |
| 1 value × 100 rows + 9 singletons | `{1}` @ 0.917 | **5 010** | 5 010 |

Same binary, same ndistinct on both sides: a 250× underestimate becomes exact
purely because the arm had an MCV list to match. That is also the answer to why
TPC-H shows nothing — its join keys are near-uniform surrogate keys, so the
inner side rarely has an MCV list at all, and where both sides do have one they
are the SAME column of the SAME table (Q21's `l_orderkey`), which makes
`nd1 = nd2` and drives `uncertainfrac` to exactly 1.0.

**The `(1 - nullfrac1)` factor.** Outer 1 000 rows / 25 % NULL keys /
`nd1 = 750`, inner `nd2 = 1 000` — the `nd1 <= nd2` branch, which returned 1.0
for a column a quarter of which can never match. Estimate **750** against an
actual of **750**; before the change it was 1 000. TPC-H declares no nullable
join key anywhere, which is why this half is likewise invisible here.

## 3. The two violations belong to neither half — checked against the oracle

This is the finding that matters for P5.9. Both violations were re-measured on
the **PG 18.3 reference cluster** (port 65432, same SF=1 dataset), because the
audit's bar is PG parity and nobody had asked what PG itself estimates.

**Q21's ANTI is not a goopg defect.** PG 18.3 estimates `rows=1` for its own
`Nested Loop Anti Join` on the same query, against the same actual of 4 003.
The reason is upstream's, stated in `neqjoinsel` (selfuncs.c): for `JOIN_SEMI`
/ `JOIN_ANTI` the `<>` clause is not priced through `eqjoinsel` at all — "if we
use the same assumption that there is more than one distinct key in the RHS
relation, then every non-null LHS row must be suppressed by the anti-join. So
either way, the selectivity estimate should be `1 - nullfrac`." With the eq
clause also at 1.0 (self-join on `lineitem.l_orderkey`, so `nd1 = nd2` in every
branch including the MCV one), `outer · (1 - 1.0)` floors at one row in PG
exactly as it does in goopg. **No estimator change can close this without
diverging from PG.** The audit needs a per-query override for Q21, the way it
already has one for Q9.

**Q18's SEMI is a real divergence, but of a different mechanism.** PG does not
plan Q18 as a semi-join: the subquery's `GROUP BY l_orderkey` makes its output
unique on the join key, so PG dedups and uses a plain inner join, estimating
117 159 rows (1 674× over the actual 70). goopg keeps the SEMI and lands on the
**0.5 punt** — `est = 5 997 241 × 0.5 = 2 998 620`, exactly half the outer,
which is the signature. The punt fires because `resolveBaseColumn` has no
`*HashAggregate` arm, so `nd2` is unknown; the inner's 1 210 559-row estimate
is far above `defaultNumDistinct`, so the clamp that would rescue it never
fires. Neither the MCV arm nor `nullfrac1` participates: without `st2` the arm
cannot be entered, and TPC-H's `o_orderkey` has no nulls.

Note for the ratchet: at 1 674× **PG itself would trip the audit's 1 000×
tripwire on Q18**. The bar P5.9 certifies against should be PG parity per
joinrel, not an absolute factor.
