# 6. Clause 6 — bushy-plan capability — **UNDISCHARGED (no instrument)**
# ---------------------------------------------------------------------------
# What the bar asks for: on every searched query where PG 18.3's EXPLAIN shows
# a bushy join spine (composite JOIN composite), goopg must be ABLE to produce
# the same composite-composite pairing over the same relset partition,
# "verified through the §4 parity gate's spine diff".
#
# **That spine diff does not exist.** `cmd/estimate-audit` — the §4 gate's
# implementation — has zero occurrences of "bushy" or "spine". Its parity
# channel compares per-joinrel ESTIMATES (`{a+b+c} goopg 3.1x | PG 2.1x`) and
# reports relsets that appear on only one side as `SHAPE (PG-only joinrel)` /
# `SHAPE (goopg-only joinrel)`. A relset name says which base relations are
# underneath a node; it does not say how they were PAIRED. Clause 6 is a
# question about pairing, so the gate cannot answer it, and has never answered
# it in runs 1-4. Run 3 recorded clause 6 as "PARTIAL" on the strength of the
# shape-divergence COUNT (67 -> 46) — that count is a proxy, not the check.
#
# Measured directly here instead, by classifying every join node in both plan
# captures as bushy iff both of its children, after unwrapping
# Hash/Materialize/Sort/Gather/Memoize/aggregation nodes, are themselves joins:
#
#   PG 18.3      Q7   BUSHY  Hash Join       <- [Nested Loop, Hash Join]
#                Q8   BUSHY  Hash Join       <- [Nested Loop, Nested Loop]
#                Q20  BUSHY  Hash Right Semi <- [Nested Loop, Nested Loop]
#   goopg ON     (none in any of the 22)
#   goopg OFF    (none in any of the 22)
#
# PG's Q7 partition, read off the §4 parity table's PG-only joinrels, is
# {customer+lineitem+n2+orders} JOIN {n1+supplier}; goopg's ON arm instead
# builds {lineitem+n1+n2+orders+supplier} JOIN customer — left-deep.
#
# This is NOT reported as a clause-6 failure. The clause admits alternative
# shapes chosen on cost-constant or stats-fidelity grounds and reserves hard
# failure for a bushy shape the search CANNOT EXPRESS. The structural evidence
# says it can: `joinSearchOneLevel` phase 2 (internal/planner/joinsearchlevel.go
# :171-222) is `joinrels.c:141-198` term for term, including the k-loop halfway
# break, the mirror-image offset and the clause-only pair gate, and it is unit-
# tested by TestJoinSearchFourRelChainOffersBushyPair,
# TestJoinSearchBushyIsClauseOnly and TestJoinSearchPairCountMatchesClosedForm.
# But those tests prove the MECHANISM on a synthetic 4-relation chain. Nothing
# proves that for Q7's, Q8's or Q20's actual relset partition the pairing was
# enumerated and then lost on cost, rather than never enumerated at all. Both
# stories predict exactly the output observed above: a left-deep winner.
#
# So the clause stands undischarged, and with it the flip. Filed as
# **M0127-P5.9-l**: give clause 6 the instrument §4 names — a search-level
# channel that records, per query, the joinrel pairings the DP actually built,
# and a comparator that asks whether PG's chosen partition is among them. Then
# clause 6 is answered by measurement, and either it passes (cost/stats
# divergence, admitted under the ratchet) or it names a concrete gap in the
# bushy phase. Either outcome is a result; the current state is neither.
