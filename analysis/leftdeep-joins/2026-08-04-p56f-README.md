# 2026-08-04 estimate audit — P5.6-f

Instrument: `cmd/estimate-audit --label <label> --timeout 150s` (`--serial` and
`--warm-stats` on by default; both load-bearing — nodes under a Gather report no
actual rows, and goopg's ANALYZE statistics are per-connection).

Cluster: `GOGC=100 GOMEMLIMIT=12GiB bench/tpch/setup_goopg.sh`, TPC-H SF=1 on
127.0.0.1:65433, database `tpch`. LEGACY planner (`GOOPG_PGSHAPED_DP` OFF).

## The baseline moved, and this is the run that re-took it

**Every audit from `2026-08-03-*` through `2026-08-04-p56eiii` was taken on an
index-free cluster.** M0127-P5.6-f-pre proved goopg's `tpch` database carried
0 user indexes against the PG 18.3 reference's 16 (a composed durability
regression, fixed forward-only). P5.6-f needs uniqueness evidence to exist at
all, so step 0 of this loop re-created the eight UNIQUE indexes the reference
declares:

```
region_pk  nation_pk  supplier_pk  customer_pk
part_pk    partsupp_pk (ps_partkey, ps_suppkey)  orders_pk
lineitem_pk (l_linenumber, l_orderkey)
```

They survive a restart (first end-to-end confirmation of the P5.6-f-pre fix on a
real cluster). The eight NON-unique FK indexes the reference also carries were
deliberately NOT created: they carry no uniqueness evidence, and adding index
paths would have moved plan SHAPE in the same run as a cardinality change — the
attribution protocol (09 §6) forbids that. The eight FK CONSTRAINTS still cannot
be restored at all (`pg_constraint` per-DB routing, the (b) half of the
P5.6-f-pre ledger row), so the declared-FK arm of the new code is exercised by
unit tests only on this dataset.

Files:

- `2026-08-04-p56f-baseline-idx.txt` / `.plans.txt` — **the re-baseline**: the
  indexes exist, the planner change does NOT. This is what the post-fix run is
  diffed against, rather than `2026-08-04-p56eiii.txt`, which was taken under a
  different schema.
- `2026-08-04-p56f.txt` / `.plans.txt` — after the change.

Creating the indexes alone changed **no violation and no ratio class**: the
re-baseline reports the identical two violations (Q18, Q21) and the identical
UNMEASURED Q9 as `2026-08-04-p56eiii.txt`. The whole delta below is the planner
change.

P5.6-g, both untouched here). No joinrel got worse. Two got much better, and
both are the mechanism firing:

| query | joinrel | re-baseline | now |

against an actual of 5 997 241**, from 479 779 280 before (80× over → exact).
Confirmed by direct EXPLAIN, since Q9 is still over the audit's timeout.

## Q9 is measurable again, but not within 150 s

`EXPLAIN ANALYZE` with a 600 s budget: **291.8 s**, 175 rows. §5.3 measured
93.9 s and §5.4 could not measure it at all, so the ordering is
93.9 s → unmeasured → 291.8 s. The cardinality defect P5.6-f owns is closed —
the estimate is exact — and what remains is class (b), plan shape:

```
Hash Join  rows=1999060  Cond: l_partkey = part.p_partkey       <- part LAST
  Hash Join  rows=5997241  Cond: (l_suppkey = ps_suppkey) AND (l_partkey = ps_partkey)
    Hash Join  rows=5997241  Cond: o_orderkey = l_orderkey
      Seq Scan orders   1 500 000
      Hash Join  rows=5997241  Cond: l_suppkey = s_suppkey
        Seq Scan lineitem  5 997 241
        Seq Scan supplier     10 000
    Seq Scan partsupp    800 000   (actual 156.8 s — build side, 32 batches)
  Seq Scan part          200 000   Filter: p_name LIKE '%green%'
```

All three hash joins carry the full 5 997 241 rows because the `part` filter
(5.3 % selective) is applied ABOVE them. PG's own plan filters `part` first and
index-scans lineitem through `lineitem_part_supp_fkidx`.

**Why the exact estimate did not move the shape.** The legacy planner does not
size its join-order search with `estimateJoin`. `estimateJoinCost`
(bushy.go:1257) has its own cardinality arm, and its production branch — the
integer DP, `costDrivenJoinOrder` OFF — computes `ndv` as *the maximum
NDistinct over every column of the edge's two tables*, ignoring the join key
entirely. The multi-edge enumeration and the superkey probe that DO exist there
(`crossEdgesBetween` + `uniqueNoFanoutRawCount`) sit in the `costDrivenJoinOrder`
branch, which M0126 closed as a no-go and left OFF. So P5.6-f reaches every
printed estimate and every post-search decision, and reaches the search itself
not at all. That is a separate, cleanly-attributed item, filed as **P5.6-f-ii**.

## TPC-DS SF0.5 gate: PASS, and the one timing move in it

`sweep-20260804-232914.txt`: **PASS=94 (57 ck-verified) MISMATCH=0
CKMISMATCH=0 ERROR=0 TIMEOUT=1 SKIP=4** — the summary line is identical to the
three preceding sweeps. Zero correctness movement.

The single TIMEOUT moved from Q72 to **Q47** (Q47 31 s → 332 s timeout; Q72
328 s timeout → 166 s; Q57 15 s → 81 s; Q53 28 s → 6 s — swings in both
directions). Q47's estimates were checked directly rather than assumed:

- every joinrel in its plan is single-pair, and a single-pair equi-join is
  unchanged by construction (`TestEstimateJoinSinglePairUnchanged`);
- its one multi-pair join is the 5-pair `v1 ⋈ v1` between two CTE scans
  (`i_category, i_brand, s_store_name, s_company_name, rn = rn+1`). Neither
  side's ndistinct resolves — a CTE scan's child is a WindowAgg and no
  resolver walks through one — so no pair is measured, the superkey prover
  proves nothing, and the estimate lands on the SAME
  `defaultEqSelectivity` + `max(l,r)` fallback it landed on before.
  `EXPLAIN` confirms `rows=1`, which is that fallback.

So Q47's plan is not something this change moved, and the bidirectional swings
plus a timeout that hops between queries across sweeps match the documented
sweep-tail confound (a goopg server that has just run a timeout query sits at
GOMEMLIMIT with GOGC=off and thrashes; CLAUDE.md, benchmark-timing hygiene).
Recorded rather than concluded: proving it needs an A/B against a reverted
binary, which is a separate run.
