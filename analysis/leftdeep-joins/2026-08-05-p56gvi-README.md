# M0127-P5.6-g-vi — re-reading the pre-fix plan-text conclusions

`20e17fa5` (P5.6-g-v) fixed a renderer that printed the **pre-qual** row
estimate on a collapsed `*Filter` wrapper's line. Every plan capture taken
before that commit therefore reports some node lines at a larger row count
than the estimator actually used. This file records how large that blast
radius is, measured rather than argued, and which closed findings rest on the
corrupted field.

## The decision rule (measured, not inferred)

Diff the two DS05 corpus captures that bracket the fix — they are line-aligned
(5 962 lines each), so a plain positional diff isolates exactly the lines the
fix moved:

- pre-fix: `2026-08-05-p56gii-plans-after.txt` (goopg `483f6ca4` + P5.6-g-ii)
- post-fix: `2026-08-05-p56gv-ds05-plans-after.txt` (same + `20e17fa5`)

```
$ python3 - <<'EOF'
import re
pre  = open('2026-08-05-p56gii-plans-after.txt').read().splitlines()
post = open('2026-08-05-p56gv-ds05-plans-after.txt').read().splitlines()

def has_filter(lines, i):                 # does this node line carry a Filter: detail?
    base = len(lines[i]) - len(lines[i].lstrip())
    for j in range(i + 1, min(i + 6, len(lines))):
        s, t = lines[j], lines[j].strip()
        ind = len(s) - len(s.lstrip())
        if ind <= base and not t.startswith(('Filter:', 'Index Cond:', 'Hash Cond:',
                                             'Sort Key:', 'Group Key:', 'Join Filter:',
                                             'One-Time')):
            break
        if t.startswith('Filter:'): return True
        if t.startswith('->'):      break
    return False

changed = {i for i, (a, b) in enumerate(zip(pre, post)) if a != b}
nodes   = [i for i, l in enumerate(pre) if 'rows=' in l and 'cost=' in l]
withf   = [i for i in nodes if has_filter(pre, i)]
print(len(nodes), len(withf),
      sum(i in changed for i in withf),
      sum(i in changed for i in nodes if i not in withf))
EOF
3283 966 836 0
```

| population | count | changed by the fix |
|---|---|---|
| node lines with `rows=` in the corpus | 3 283 | 836 (25.5 %) |
| …of which carry a `Filter:` detail | 966 | **836** |
| …of which carry **no** `Filter:` detail | 2 317 | **0** |
| non-node lines differing | — | 5 (3 provenance header lines + 2 psql column-width lines) |

**So the rule is exact and biconditional in practice:** a `rows=` read out of
a pre-`20e17fa5` capture is trustworthy **iff its node line has no `Filter:`
detail beneath it.** No line without a `Filter:` moved, anywhere in 99 plans.
The 130 `Filter:`-carrying lines that did *not* move are the details that
never came from a collapsed wrapper (a scan's own qual field, `Filter: (true)`
on a CTE scan, an index scan's recheck).

Magnitude on the 836 affected lines: overstatement factor **median 9×, p90
18 000×, max 1 920 800×**, across **96 of 99 queries**. The field is not
slightly wrong where it is wrong.

Two corollaries worth keeping:

- The rule applies to **join nodes too**, not only scans — Q1's
  `Hash Join (INNER) … Filter: (date_dim.d_year = 2000)` went `rows=716` →
  `rows=3`. "Only base relations are affected" would have been wrong.
- Plan **shape** is immune by construction (a renderer cannot reach plan
  selection), and §5.13 proved it for this corpus by normalising `rows=`
  before diffing: 6 residual lines, all header.

## Verdicts on the closed findings that quote plan-text row counts

Checked against the archived captures the findings themselves cite, applying
the rule above.

|---|---|---|---|

| **M0125-0026 C2 / Q5** ("`date_dim` costed at its full 73 049") | `date_dim` 73 049 | no (`goopg-warm-m0125-0037/q5.txt`: all 7 `date_dim` scans bare) | **SURVIVES** |

**C5's arithmetic is the interesting one, because it corroborates the fix
rather than falling to it.** C5 read `359 432 (web_sales) × 365.25 (date_dim
after d_year) = 131 280 738` against a rendered join estimate of
`rows=131280740` — but 365.25 is nowhere in that capture's plan text (the
`date_dim` line reads 73 049). It is `73 049 × 0.005`, i.e. `DEFAULT_EQ_SEL`
applied to the equality, and C5 obtained it by *dividing* the join estimate.
That is exactly P5.6-g-v's conclusion arrived at independently and a year of
loops earlier: the **estimator** was carrying the post-qual number all along,
and only the rendered line disagreed. C5's claim — that the equi-join key
contributes no selectivity — is unaffected either way; it compares the join's
estimate to the product of the estimator's own inputs.

## The one correction owed

§5.13 (and `20e17fa5`'s message) says the row-count half of M0125-0026's
"`date_dim` is costed at 73 049" evidence "was an artifact". **That is too
broad.** The artifact reading only applies where the scan carries a collapsed
`Filter:`, and C2's whole point is that in goopg it does *not* — 66 of 68
qualifying `Filter:` lines sat on a join node, which is why the `date_dim`
scans render, correctly, at their full 73 049 rows. C2's row-count claim is
faithful for the same reason its placement claim is true. The two captures
that *are* corrupted are C2's two named exceptions — the scalar-SubPlan
`date_dim` scans in Q14 and Q54, which print
`Filter: (((d_year = 2000) AND (d_moy = 12)) AND (d_dom = 3))` beside
`rows=73049` — and no conclusion rests on their row counts; they are cited
only as placement exceptions.

Net: **of the closed findings that quote a scan or aggregate row count from
plan text, none needs re-deriving.** The corrupted field is pervasive (25.5 %
of node lines) but the findings that survived triage happened to quote the
unfiltered lines, because the unfiltered lines are what C2/C5/C6 are *about*.

## What this does not clear

Captures under `analysis/` taken before `20e17fa5` are **not** being
re-captured; they stay as the historical record they are. Any future loop
reading a `rows=` out of one must apply the rule above first. The rule is
cheap to apply — look for a `Filter:` line — and is now recorded in 09 §5.14
so it does not have to be re-derived a third time.
