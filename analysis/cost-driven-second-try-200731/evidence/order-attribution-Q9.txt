## Cardinality chain analysis

| Join step | Default estimate | Cost-driven estimate | Actual (from exec) |
|-----------|-----------------|---------------------|---------------------|
| nation ⋈ supplier | — (last) | 1,250 | ~10K |
| … ⋈ lineitem | — | 37,482,756 | ~6M |
| … ⋈ partsupp | — | 149,931,024,000 | ? (FK-constrained) |
| … ⋈ orders | — | 1,124,482,680,000,000 | ? (FK-constrained) |
| … ⋈ part | — | 5,888,930,250,208,968 | 175 |
| orders ⋈ partsupp ⋈ lineitem (MHJ) | 179,917,230,000,000 | — | ? |

Key observation: In the cost-driven plan, each successive FK join MULTIPLIES the
estimated cardinality instead of joining on a key. The chain:
  nation(25) × supplier(10K) / ndistinct = 1250         (OK)
  1250 × lineitem(6M) / ndistinct = 37M                   (already ~6x too high)
  37M × partsupp(800K) / ndistinct = 1.5e11              (explosion)
  1.5e11 × orders(1.5M) / ndistinct = 1.1e15             (further explosion)
  1.1e15 × part(200K) / ndistinct = 5.9e15               (final absurdity)

The default MHJ plan masks this: the single MHJ estimate (1.8e14) is equally
wrong, but the subsequent dimension joins (part, supplier, nation) with filters
bring it down: 1.8e14 → 1 → 50 → 6 → 3.

## Root cause

The join cardinality estimator computes NDistinct-based selectivity without
accounting for foreign-key constraints. When a FK-PK join chains N tables, the
estimator treats each join column as an independent random variable, causing
multiplicative error amplification.

In the cost-driven plan the small dimension tables are joined first, so the
"base" cardinality starts reasonable (1250) but then each successive FK join
with a large fact table appears to explode the row count. The cost model sees
each intermediate hash table as impossibly large, which should make this plan
look terrible — yet the planner still picks it, suggesting the cost model's
alternative (big-tables-first) has even worse estimates, OR the cost of the
alternative path is dominated by the MHJ's own absurd estimate.

## Classification: (a) cardinality estimate

Specifically: **multi-level FK join cardinality compounding**. The ndistinct-based
selectivity formula does not recognize that joins on FK-PK columns are
semantically constrained (each fact row matches exactly one dimension row),
so the estimator treats them as independent Bernoulli trials across the
Cartesian product, causing O(n^k) blowup for k-level chains.

## Routing

→ M0126-0010: bounded cardinality fix. Candidate approaches (constrained by
  M0126-0010 prohibitions — no global NDistinct rewrite, no penalty multipliers):
  1. FK-aware join selectivity: when a join column is a FK referencing the other
     side's PK, the selectivity should be 1/max(ndistinct_probe, ndistinct_build)
     rather than the product formula.
  2. Join-key ndistinct cap: the estimated output rows of a hash join should
     never exceed max(|outer|, |inner|) for a FK-PK join.
