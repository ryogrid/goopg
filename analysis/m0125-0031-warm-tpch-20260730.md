## 2. §D3's invariant is now MEASURED, not asserted: the relsize fallback is inert when warm

`plan-diff` against the `warm-stats-base` baseline (captured under the shipped default,
i.e. stage 2, on this warm cluster) with the server started at
`GOOPG_RELSIZE_FALLBACK=0`:

```
MODE=structural   → 22/22 MATCH, rc=0
MODE=strict-text  → 22/22 MATCH, rc=0
```

Byte-for-byte identical plans for all 22 queries. Design §D3's invariant — *flag-on and
flag-off are indistinguishable in any ANALYZEd state*, resting until now on
`relSizeFallbackRows`'s `RowCount > 0` early return plus one unit test — is confirmed
end-to-end on the real bench cluster. Two consequences:

1. **M0125-0003/-0005 is an S-cold-only mechanism, exactly as the programme's design
   claims.** On a warm cluster it is not a risk *or* a benefit; the 1.40× c1→c2 win is
   a property of never-analyzed relations. Anyone re-opening the default flip should
   read it as "the S-cold safety net", never as a warm-cluster tuning knob.
2. **w1 and w2 are the same execution plan, so every w2/w1 ratio in §1 is pure
   run-to-run noise** — which makes this run a free calibration of the harness.

## 3. Noise-band correction: this harness's per-query band is ~±17 %, not ±4 %

The c-arm doc set its noise band from Q16/Q17/Q19 at 1.02–1.04× and read Q14's 1.08× as
inside it. With plans now *proven* identical, w1→w2 moved **Q6 1.17×** (3.82 → 4.47 s)
and **Q10 1.16×** (13.60 → 15.72 s), with Q16 at 1.09×. So:

- **A single-run per-query ratio below ~1.2× on a sub-20 s query is not evidence.**
  That retires the "Q10 is 1.24× slower warm" reading a naive look at §1 invites: the
  identical-plan pair spans 1.16× on that very query, so 1.24× is at best marginal and
  needs repeated runs before it is called a regression.
- What survives the band comfortably: **Q8 (8.5×)** and **the 21-query stream
  aggregate** (−15.0 %, where per-query noise averages down), plus the c-arm doc's own
  large wins (Q9 3.29×, Q12 3.43×, Q10 2.58×).
- The `analysis/tpch-relsize-fallback-20260730.md` band statement is superseded by this
  paragraph; its win/regression *conclusions* are unaffected because every one of them
  is outside the wider band too.

## 4. What warm statistics do NOT fix: Q21 is TPC-H's shape-class timeout

**Q21 times out in all four arms** — S-cold or warm, flag off or stage 2 (612 / 672 /
381 / 384 s against a 300 s cap; peak RSS 14.4 GB in both w-arms, i.e. it pins the
15 GB cgroup ceiling). It is the only TPC-H query in the timeout class, and it is now
known to be **independent of both cardinality inputs**: relation sizes alone do not
rescue it (c1→c2), and neither do full statistics with MCVs and histograms (c2→w2).

This is precisely the split M0125-0031 predicted: *no cardinality input fixes a
rescan-per-outer-row shape.* Q21 belongs with the TPC-DS shape class (M0125-0026's
suspects a/d/e), not with its size-starved members, and it needs a plan-shape fix.
Filed as **`M0125-0032`** with this measurement as its baseline.

## 6. What this run cannot see

- **One run per cell.** §3 quantifies the resulting band; no per-query claim under 1.2×
  is made on this data.
- **SF=1, one cluster, one host.** The warm-up ANALYZE ran per chunk on the same
  standing cluster (`bench/tpch/runtime_goopg/data`), so all four arms share its load —
  which is what makes them comparable, and also what makes them not a scale study.
- **No PG arm.** This is a goopg-vs-goopg regime comparison. The PG reference cluster
  (65432) was not touched, so nothing here says how far TPC-H is from the oracle.
- **The chunk boundaries are visible in `host: load`** (up to 4.68 at a chunk start,
  which is the previous chunk's own tail draining, not foreign load). Per-query server
  restarts hold server age constant, which is the confound that mattered.
- **pg_statistic is incomplete for wide text columns** (M0125-0029's TOAST gap, ledger
  row 607): `partsupp.ps_comment` and friends have no histogram. The warm regime
  measured here is therefore "warm except for oversized histograms" — closing that gap
  could move these numbers again, in either direction.
