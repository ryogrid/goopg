# PG 18.3 と goopg のクエリ別実行時間比較 (TPC-H SF1 / TPC-DS SF0.25 / TPC-DS SF1)

作成日: 2026-10-23 (作成時の HEAD は `606717ffc`。測定はそれ以前のビルドで行われたもの)

> **要約**: TPC-H SF1 では goopg ≈ PG の 1.4 倍 (幾何平均)。TPC-DS SF0.25 では ≈ 2 倍 (中央値。条件差は双方向にある)。
> TPC-DS SF1 は現行条件での比較データがなく、唯一比較できる Q74 は PG が極端に遅いクエリなので全体の傾向は示さない。
> **注意**: 比較相手の PG 18.3 は `--enable-cassert` (アサーション有効) ビルドで、本番向けビルドより遅い。
> そのため、どの比も goopg に有利な側に偏っており、本番向け PG と比べた差はこれより大きいと考えるべき。

## 0. この文書について

- **目的**: plan-parity 作業 (goopg のプラン形状を PG と一致させる作業) がほぼ完了した現時点で、PG 18.3 と goopg の
  性能差を **おおまかに** 掴むこと。
- **再測定はしていない**。Ralph ループ (および過去セッション) が既に測定・保存していた結果だけを集約した。
  性能観点で実質的に同一条件と見なせる PG/goopg の対を選び、選べなかったものはその旨を明記した。
- **PG 側のビルド条件 (全ベンチマーク共通)**: 参照クラスタ (`:65432`、`:65438`) はどちらも
  `postgres/local_install/bin/postgres` (2026-07-16 ビルド) で動いている。`pg_config --configure` は
  `--enable-cassert --enable-tap-tests` で、`-O2` 最適化だが `USE_ASSERT_CHECKING` が有効 (これにより
  `CLOBBER_FREED_MEMORY` と `MEMORY_CONTEXT_CHECKING` も有効になる)。LLVM なし (JIT 不可)。アサーション有効ビルドは
  本番向けビルドより遅いことが知られているため、**PG の実行時間は本番向けビルドより長めに出ており、対PG比は
  goopg に有利な方向に偏っている**。その大きさは今回測定していない (このリポジトリに非アサーションビルドの PG 計測はない)。
- TPC-H と TPC-DS SF0.25 の goopg バイナリは、いずれも 2026-10-22〜23 の M0122-0012 (executor 性能スライス) 期の
  ビルドで、測定ごとに少しずつ異なる。目的が概況把握なので許容している。TPC-DS SF1 の出典はこれより古い (§4.1)。
- **対PG比 = goopg 実行時間 ÷ PG 実行時間**。1.00 より大きいほど goopg が遅く、1.00 未満なら goopg の方が速い。
- 表は全クエリを省略せず掲載している (TPC-H 22 本、TPC-DS 各 99 本)。
- 機械可読な元データ (英語の注記つき) を同じディレクトリの `data/` に置いた:
  `data/tpch-sf1.tsv`、`data/tpcds-sf025.tsv`、`data/tpcds-sf1.tsv`、`data/tpcds-sf1-goopg-recent-only.tsv`。

  スイープは行われていない。10 月の SF1 作業はプラン形状の一致確認 (EXPLAIN のみ、99/99 一致) で、実行時間は
  記録されていない。
  - 比較可能な対は Q74 (goopg 0.61 倍、つまり goopg の方が速い) の 1 本だけ。ただし Q74 は SF0.25 でも PG が極端に
    遅い 6 本の 1 つであり、SF1 全体の傾向を示すものではない。
  - Q47 / Q68 / Q96 の 3 本は 10-13 の同一セッション計測だが、goopg 側が再ロード前の旧コーパスのため準比較可能
    (goopg の値は過大)。
  - 残りの 95 本は、条件がまったく異なる 7 月の値を参考として載せている (§4)。

### 2.3 注意点

- **Q15 は比較対象の値がない**。runner の Q15 は `CREATE VIEW` を発行する (DDL) ため、読み取り専用の参照クラスタ
  `:65432` では実行しておらず、PG 側の 10 月の計測が存在しない。goopg 側の warm ハーネスも Q15 を飛ばしている。
  参考値として goopg 単独の acceptance arm (起動直後の 1 回実行、部分的に cold、`tmp/accept-s65`、2026-10-23)
  ではビュー定義の SELECT 単体 1.36 s、ビューを参照する主クエリ 2.79 s (CREATE VIEW 自体は 0.03 s)。
- PG と goopg の測定は約 31 時間離れている (同一セッションではない)。ホスト負荷はどちらも記録されていない。
- PG サーバは長時間稼働で完全に warm。goopg サーバは 2 パス目の時点で起動後約 20 s (1 パス目で shared buffers を
  充填済み、OS ページキャッシュも warm)。
- goopg の Q2 / Q5 / Q7 は同一バイナリでも実行ごとに二峰性を示す (Q2 は 0.33〜0.70 s と 0.37 s 幅で振れる)。これらのクエリの差はノイズを含むものとして読むこと。
- Q11 / Q19 / Q22 は 100 ms 未満で runner の分解能 (10 ms) に近く、比は粗い。
- slice 54〜69 (10-22 夕方〜10-23) は TPC-DS 向けの改善で、その後の warm TPC-H 計測はない。単発の acceptance arm の
  合計は slice 54 → slice 65 で 26.22 s → 24.47 s (約 −7 %) なので、現 HEAD の goopg は表の値よりやや速い可能性が高い。

### 3.2 残っている条件差 (比を読む前に確認すること)

1. **shared_buffers が一致していない: goopg 128 MB、PG 2 GB**。`data-sf025/postgresql.conf` では shared_buffers が
   コメントアウトされたまま。09-17〜10-23 の全起動ログで `shared_buffers_slots=16384` (= 128 MB)。09-06 の修正
   (`0df7dc930`) は SF1 / SF0.5 クラスタにしか入っておらず、09-11 に作られた SF0.25 クラスタには入っていない。
   データ量はファクト表全体で約 0.5 GiB と推定され (store_sales だけで約 116 MB。SF0.5 で計測した 232 MB の半分からの推定。
   データベースディレクトリ全体は 756 MB)、goopg は OS ページキャッシュからの再読み込みを繰り返す。ディスク I/O ではなくコピーコストだが、スキャン主体のクエリで goopg に不利に働く。
2. **warm さの非対称**: goopg は新規起動サーバでの 1 パス (バッファプールは cold、OS ページキャッシュは毎時の
   スイープで warm)。PG は長時間稼働サーバでの 1 パス (バッファプールは warm だが SF1 の `tpcds` DB と共有)。
   どちらもウォームアップパスはない。どちらに有利かはクエリによる。PG 側には初回読み込みで膨らんだと思われる値が
   いくつかある (Q72: 1,117 ms、warm 再実行では 600 ms。Q7 / Q10 / Q21: 1.8 / 1.4 / 0.7 s、09-11 計測ではいずれも約 0.1 s。
   Q2 / Q3: 558 / 142 ms、09-11 計測では 176 / 19 ms。Q23: 3.55 s、10-21 計測では 1.77〜1.97 s)。
   PG の再実行値 (warm) がある場合、それを基準にした比を備考に参考として併記した (Ralph ループの記録にある再実行値に
   基づく。基準に使った値の選び方はクエリによって統一されていないため、目安として読むこと)。
   また、PG は単発値、goopg は 3 スイープの中央値なので、一時的な停滞の除去は goopg 側にしか効いていない。
3. **測定日が異なる**: PG は 10-22、goopg は 10-23。PG のバイナリと設定は変わっていないので、影響はホスト負荷だけ。
4. **クライアントオーバーヘッド**: どちらも接続確立と結果転送を含む (PG は `/dev/null` へ、goopg はファイルへ出力)。
   50 ms 未満のクエリ以外では無視できる。
5. **PG が極端に遅い 6 本**: Q1 / Q4 / Q6 / Q11 / Q54 / Q74 は PG で 2〜59 s かかり、goopg では 0.3〜11 s。
   09-11 の oracle 計測でも同じ桁なので、ノイズではなくこのデータ上での PG のプラン挙動。合計値を支配するため、
   §1 では合計比をこの 6 本の除外前と除外後の両方で示した。

### 4.3 SF1 についての所見

- 比較可能な Q74 は goopg 543 s、PG 896 s で **goopg の方が速い (0.61 倍)**。CTE `year_total` の CTE Scan 同士の自己結合 (Nested Loop) が支配的な
  CPU 律速のクエリ。ただし Q74 は SF0.25 でも PG が極端に遅い 6 本の 1 つであり、SF1 全体の傾向を示すものではない。
  また goopg の 543 s は 10-19 の値で、その後の高速化により nightly 10-23 では 257 s まで下がっている (条件の異なる
  goopg 単独値)。現在の goopg ならおよそ 0.3 倍程度と推定されるが、PG と対にした計測ではない。
- 出典 C の 7 月の比 (多くが数十〜数百倍) は、統計なし・128 MB・旧バイナリでの値であり、**現状を表していない**。
  最近の goopg 単独値 (nightly 10-23) では、記録のある 63 本のうち 60 本が 0〜4 s に収まっている。
  例外は Q1 (163 s)、Q74 (257 s)、Q95 (43 s)。nightly 対象外の Q14 (10-07 に 218 s)、Q81 (同 164 s) も重い可能性がある。
- 現状の SF1 の性能差を per-query で把握するには、両エンジンで改めて SF1 スイープを取る必要がある (今回の範囲外)。
  その際、Q4 / Q11 / Q31 / Q36 / Q70 / Q86 / Q88 には 9 月以降 goopg の SF1 計時が一切ないことに注意。

## 6. 本番ビルド (非 cassert) の PG 18.3 との比較 (2026-10-23 追加計測)

§2・§3 の PG の値は `--enable-cassert` ビルドでの計測だった (§0)。そこで、アサーションを無効にした PG 18.3 を

### 6.5 残っている条件差・注意点

- **goopg の値は §2・§3 のまま** (TPC-H は 10-22、TPC-DS は 10-23 早朝の計測)。PG は 10-23 16 時台の計測で、日時が異なる。
- **cassert ビルドとの差は、ビルドの違いだけによるものではない**。§2・§3 の PG の値と比べると、TPC-H は合計 12.26 s → 8.75 s
  (クエリ別比の幾何平均 1.38 倍)、TPC-DS は合計 189.6 s → 85.8 s (同 1.57 倍) と速くなっている。ただしこの差には、ビルドの違いに
  加えて、TPC-H ではデータのロード方法 (再ロード) と新規起動サーバでの計測、TPC-DS では shared_buffers 2 GB → 128 MB、
  単発値 → 3 スイープの中央値、長時間稼働サーバ → 新規起動サーバ、出力先 (`/dev/null` → ファイル) の違いも含まれる。
  ビルドの違いだけの効果は測っていない (同一条件での cassert ビルドの対照計測は行っていない)。
- TPC-H のヒープは参照より最大 1.2 % 大きく、可視性マップは全ページ設定済み (参照は一部のみ)。統計とプラン形状は参照と同一。
- TPC-H Q15 は §2 と同様に比較対象外 (goopg 側に warm な計測がない)。
