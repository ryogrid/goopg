## 1. Measurement method

Added `BuildTimeNs` to `HashJoinStats` (`internal/executor/join_batch.go`)
and a timer around `buildLazyHashTable` (`internal/executor/operators_join_agg.go`).
EXPLAIN (ANALYZE) text format reports `Build Time: N ms` on the hash-join
detail line. Timed queries via `psql` on the standard TPC-H cluster (port 65433).

## 2. Data

Four equi-join queries covering the TPC-H dimension-size spectrum, each counting
`lineitem ⋈ dim` with the dimension as the hash build side:

| dim table | build rows | build time | total exec | build % | batches | notes |
|---|---|---|---|---|---|---|
| `supplier` | 10 K | 21.6 ms | 3,145 ms | 0.7 % | 1 | negligible |
| `customer` | 150 K | 324.5 ms | 939 ms | 34.6 % | 1 | medium dim, fast probe |
| `part` | 200 K | 498.8 ms | 3,966 ms | 12.6 % | 1 | medium dim, large probe |
| `orders` | 1.5 M | 7,518.7 ms | 18,324 ms | 41.0 % | 2 | large dim, spill (388 MB) |

The `customer` row is the most instructive: total time is only 939 ms because
Gather parallelises the probe scan, so the serial 324 ms build is 35 % of the
total. As builds grow, the fraction increases — the 1.5 M-row `orders` build
takes 7.5 s (41 %) and spills to 2 batches.

## 3. Existing confirming evidence

- **`docs/design/parallel-query/IMPLEMENTATION-TODO.md` §P8 post-mortem (line 672):**
  Q13's LEFT join forces `orders` (1.5 M rows, 10× the probe side) onto the
  build side. Parallelising the probe gave ~1.5 % gain — the build is the
  bottleneck. The reopen condition is explicitly noted as MET.

- **`docs/design/parallel-query/12-parallel-multi-way-hash-join.md` §5.1:**
  Q3 with parallel MHJ peaks at 2 workers then degrades because every worker
  rebuilds the 1.5 M-row `orders` table. §6: "the reopen condition is now MET."

## 4. Verdict: GO

Cooperative parallel hash build is justified. The serial build is **not** the
bottleneck for every hash join — small dimensions (supplier, nation, region)
build in under 25 ms, and the probe dominates. But it **is** the bottleneck
in every case where the build side is non-trivial:

- **Medium dimensions** (customer, part, ~150–200 K rows): build is 12–35 %
  of total when the probe is parallelised.
- **Large dimensions** (orders, 1.5 M rows): build is 41 % and spills.
- **LEFT joins** (Q13): the larger side is forced onto the build by the join
  type, making the build the dominant phase.
- **MHJ rebuilds** (Q3): each worker rebuilds the same table — N× waste.

## 5. Recommended implementation decomposition

Per `IMPLEMENTATION-TODO.md` lines 676–682 and `10-roadmap.md` line 170, two
candidate follow-ups in increasing order of cost:

1. **Parallelise the build's scan+filter, keep insertion serial**
   (producer/consumer). Q13's build side carries a `NOT LIKE` filter over
   1.5 M rows; a producer/consumer split parallelises the predicate while one
   goroutine owns the map. Much cheaper than PG's design; probably most of
   the win for TPC-H.

2. **Genuinely concurrent build** (sharded or per-worker-partial-then-merge),
   PG's `Parallel Hash` equivalent. Higher engineering cost; needs a
   concurrent-map or sharded-locking design and a barrier protocol.

Recommend starting with (1): measure the scan+filter parallelisation alone,
then decide whether (2) is still needed.
