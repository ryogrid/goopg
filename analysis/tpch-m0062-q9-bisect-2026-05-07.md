# M0062 — Q9 LIKE Regression Root-Cause Bisect (2026-05-07)

## Outcome

**Breaking commit:** `13fad01` — `feat(planner,executor): M0054-0006
Nested-Loop Index Join` (2026-05-05).

When NLI is disabled (`SET enable_nestloop_index = off`) on the
current HEAD, Q9 runs without raising SQLSTATE 42883 (the query
just times out for unrelated reasons — that's M0062-0001 territory,
not the LIKE error). With NLI on, Q9 immediately fails with
`operator LIKE requires string operands (got left.Kind=5
right.Kind=3)` — i.e. **`p_name`** is being read at runtime as
**`KindTime`** (a date column), not `KindString`. This is a
column-index resolution bug, not a Datum-Kind coercion bug.

## Why the forward fix in commit `aa2c50e` doesn't resolve Q9

`aa2c50e` makes `evalBinary`'s LIKE branch accept `KindBytes` as
UTF-8 text. That fix is independently correct (varchar values can
legitimately reach the comparator as bytes via spill / TOAST
paths), but it is not Q9's actual problem. Q9 hands LIKE a
`KindTime` Datum because the Filter's `p_name` `*ColumnRef.Index`
resolves into the wrong slot of the joined-row schema after NLI
substitution.

The upgraded error message in `aa2c50e` (now logs both kinds) was
the diagnostic that made this distinction visible without a
re-bisect.

## Hypothesis (NLI-side)

`internal/planner/nl_index_join.go::nliRewrite` substitutes a
`*Join` with a `*NestedLoopIndexJoin` whose `schema` is built as
`outer.Output() ++ inner.Output()` (line 372–374). When the
original Join had `BuildLeft=true` — i.e. the *probe* (outer-row
driver) was on the right — `outer = j.Right` and the new schema
becomes `Right ++ Left`, which is reversed relative to the
original Join's `Left ++ Right` schema. Parent operators
(`*Filter`, parent `*Join`, etc.) carry `*ColumnRef` indices that
were resolved against the original `Left ++ Right` layout; after
NLI substitution those indices point at the wrong slots.

For Q9 specifically, the chain is

```
Filter ( p_name LIKE '%green%' AND ...)
  → NestedLoopIndexJoin (orders inner; outer = the inner NLI)
    → NestedLoopIndexJoin (partsupp inner; outer = MHJ)
      → MultiHashJoin (part, supplier, nation, lineitem)
```

`p_name` lives in `part`. If either NLI re-orders its schema vs.
its original Join, the `*ColumnRef` for `p_name` (resolved against
the pre-NLI layout) ends up pointing at a date column from
`lineitem` or `orders` — and the runtime sees `Kind=KindTime`.

This hypothesis still needs verification by reading the explicit
column indices the planner assigns vs. observing the actual
runtime row. The verification belongs to **M0062-0006**
(below).

## Action

A new sub-task **M0062-0006 — NLI schema-substitution column
indices** should be opened to fix the column-index re-resolution
bug. It is the only blocker for Q9 once `aa2c50e`'s forward fix
is in place.

Until M0062-0006 lands, the operational workaround is `SET
enable_nestloop_index = off` for affected sessions. This is also
the kill-switch the original NLI design (`docs/design/0053-0002`)
provisioned for exactly this kind of regression.

Q14 — which the M0054-0006 commit message specifically called out
as benefiting from NLI — is not affected by this bug because the
Filter above its NLI references only the build side's columns,
not the inner side, and the build side keeps its original
position.
